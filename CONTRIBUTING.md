# Как вносить изменения

Для того, кто правит код Wynd: как собрать и проверить, как здесь называют вещи, что значат номера в коде и коммитах, как вести справочники, CHANGELOG и версию. Как поставить и обслуживать инстанс — в [README](README.md).

## Сборка и тесты

Нужны Go 1.26 и Node 22 с npm. Клиент вшивается в бинарник через `go:embed` из `web/dist`, поэтому порядок один: сначала клиент, потом Go.

```bash
cd web && npm ci && npm run build
go build -o dist/wynd ./cmd/wynd
```

Для работы — `go run ./cmd/wynd` и `npm run dev` в `web/` (Vite на :5173, `/api` проксируется на :7676); на Windows `scripts\run.bat`. Без `web/dist` падает уже `go vet ./...` — `web/embed.go` не находит, что вшивать.

**Ворота** — `scripts\test.bat` на Windows, `make test` на Unix, то же в CI Gitea (`.gitea/workflows/ci.yaml`, плюс `docker build`):

| Шаг | Что ловит |
|---|---|
| `go vet ./...`, `go test ./...` | Сервер: инварианты хроники, панели и архива, сторожа маршрутов и версии |
| `go build ./cmd/wynd` | Бинарник собирается с текущим `web/dist` |
| `npm run check` | `svelte-check`: типы и разбор `.svelte` |
| `npm run check:ui` | Сторож библиотеки интерфейса (`web/scripts/ui-guard.mjs`) и храповик инлайн-стилей |
| `npm run test` | Vitest: ядро клиента, компоненты, файл лицензий |
| `npm run build` | Клиент собирается |

Состав везде один. В Makefile и CI клиент собирается первым — без `web/dist` падает `go vet`; `test.bat` гоняет Go первым и опирается на `web/dist` от прошлой сборки, так что на чистом клоне сначала `npm run build`. Почта на настоящих релеях — отдельно, `scripts\test-integration.bat` (учётки в `dev/`, образцы в `internal/mail/testdata/`). Два участника в одном браузере: `http://127.0.0.1:5173` и `http://localhost:5173` — разные origin, у каждого свой IndexedDB. Правку экрана проверять и в `vite build` + бинарнике, не только в `vite dev`.

## Глоссарий

Слова продукта, которые встречаются в коде, коммитах и справочниках. Подробный образ — [wynd.html](docs/wynd.html).

| Термин | Что это | В коде |
|---|---|---|
| Круг | Закрытая группа со своим журналом; единственная единица общения | `circle`, `circles`, `circle_id` — везде, не `group`/`space` |
| Улочка | Список кругов участника на всех серверах — главный экран клиента (кадры 2.*) | `routes/circles/+page.svelte`, `PayStreetBanner` |
| Учётка | Почта на этом сервере; входит по коду из письма | `accounts`, `account_id`; в панели — `/admin/people`, в API — `/admin/accounts` |
| Лицо | Имя и аватар человека в одном круге; версионно, учётку наружу не выдаёт | `identities`, `identity_id`, `identity_names` |
| Хроника | Журнал событий инстанса — источник sync; пишется в одной транзакции с проекцией | `internal/chronicle`, таблица `events`, курсор `seq` |
| Снимок | Текущее состояние экрана круга (лента, дни, сетка), которое читает клиент | `snapshot*.go`, IDB `snapshots` |
| Сказанное | То, что участник написал сам: запись, комментарий, реакция, название и обложка дня; у каждого своё окно правок | `posts`, `comments`, `reactions`, `day_titles`, `day_covers` |
| День | Проекция записей по дате отнесения; своё название и обложка | `days`, ключ `(circle_id, entry_date)` |
| Отрезок | Интервал, в котором участник видит круг; повторный вход — новый отрезок | `membership_spans`, `[started_at, ended_at)`, `can_read` |
| Вышедший с доступом | Ушёл, но читает то, что было при нём; не пишет | `memberships.status = 'left_with_access'` |
| Окно правок, летопись | Сколько после публикации можно править своё; 0 — летопись, правок нет | `edit_window_sec`, `SetEditWindow` |
| Цикл архивации | Круг упёрся в квоту: участники скачивают архив до срока, потом старое до отсечки стирается | `archive_cycle_started_at`, `archive_cutoff_date`, `archive_deadline`, `cutoff_locked_at`, `PurgeBeforeCutoff` |
| Квота | Потолок места круга и инстанса | `quota_bytes`, `quota_custom`, `storage_quota_bytes`, `storage_quota_disk_percent` |
| Шлюз оплаты | Закрывает круги участнику с истёкшей подпиской, когда оплата включена | `RequirePaidParticipant`, `payment_required`, маршруты под `paid` |
| Очередь | Офлайн-записи и комментарии клиента до отправки; повтор идемпотентен | IDB `queue`, `client_id`, `drainQueue` |

## Номера в коде и коммитах

**Кадры макета.** `docs/visual/screens.html` — эталон экранов, у каждого кадра якорь `#eN-M`; в тексте тот же кадр пишется `N.M`. Раздел `N`: 1 — вход, 2 — улочка, 3 — круг, 4 — запись, 5 — четыре взгляда (дни, сетка, карта, поиск), 6 — настройки круга, 7 — приложение, 8 — тёмная тема, 9 — панель, 10 — оплата. `9.10` = `#e9-10` = `/admin/general`; `6.21` — живые ссылки круга; `e4-14` — якорь кадра 4.14. Какой маршрут рисует кадр — таблица «Маршруты» в `client-reference.md`. Кадры не перенумеровываются.

**Пункты плана.** Коммит начинается с плана и пункта: «План 42 / GUI-4: …». Пункт — префикс-категория и номер из раздела A плана (`SEC` — безопасность, `DOC` — документация, `GUI`, `REF`, `CPX`, `LEG`, `DEC` …). Выполненный план удаляется, поэтому номер в старом коммите или комментарии («план 41 / 4.5») ищется в истории: `git log --all -- docs/plans/41-*`. Решение из плана переносится в справочник — в коде ссылаются на раздел справочника, а не на пункт плана.

## Справочники и комментарии

Решения живут в `docs/reference/`: сервер, клиент, библиотека интерфейса. Формат: подзаголовок на экран или тему, абзац не длиннее 600 знаков, ячейка таблицы — 300. Не влезает — подпункты, а не длиннее абзац. Новое решение записывается тем же коммитом, что и код.

Комментарии в коде: неочевидное решение объясняется у кода одной-двумя строками со ссылкой на раздел справочника; у каждого теста-инварианта — строка с инвариантом; экспортируемой функции Go — doc-комментарий. Процент комментариев не поднимать ради числа.

## Исходники: Gitea и GitHub

Рабочий remote — Gitea (`https://gitea.mixdep.ru/mix/wynd`), и путь модуля Go — тоже (`gitea.mixdep.ru/mix/wynd`). Публичный адрес исходников (AGPL §13) — зеркало на GitHub `https://github.com/mixeme/wynd`; оно поднимается **к публичному релизу**, до него `git ls-remote` отвечает «not found», и это ожидаемо, пока инстанс не отдан сторонним участникам.

Адрес записан один раз — `version.SourceURL` в `internal/version/version.go`. Сервер отдаёт его полем `source_url` в `GET /api/v1/instance`, клиент берёт оттуда (`$lib/instance/source.svelte.ts`) во всех местах: «поднимите свой» на `/join` и `/circles/new`, «исходный код» в настройках и в футере `/admin`. Зашитый в клиент адрес — только запас на случай сервера старой версии. Форк меняет одну константу. Не разносить адрес по экранам заново.

Остальные вхождения — не код клиента и правятся вручную: `README.md`, `Documentation=` в `deploy/systemd/wynd.service`, OCI-метки образа. Кадры `docs/visual/screens.html` — эталон, их не трогают.

## Лицензии компонентов

Уведомления сторонних лицензий лежат в `web/static/THIRD_PARTY_LICENSES.txt` и отдаются клиентом по ссылке «лицензии компонентов» (настройки участника и футер `/admin`). Файл собирается скриптом `web/scripts/third-party-licenses.mjs` (`npm run licenses` в `web/` или `make licenses`) из `package-lock.json` (боевые зависимости) и `go list -deps ./cmd/wynd` (модули, попавшие в бинарь); тексты берутся из `node_modules` и кеша модулей Go.

Файл лежит в репозитории, а не собирается при `npm run build`: стадия `web` в образе — `node:22-alpine`, Go там нет. Чтобы он не устарел молча, `src/test/licenses.test.ts` пересобирает его и сравнивает с сохранённым — **после смены зависимостей `npm run licenses` обязателен**, иначе ворота красные. Зависимость без файла лицензии и без поля `license` в `package.json` — отказ сборки файла: разбирать руками.

## Аудит безопасности: когда нужен повторный проход

Отчёты: [2026-09-03](docs/security-audit-2026-09-03.md) (срез 0.1.14) и [2026-09-22](docs/security-audit-2026-09-22.md) (срез 0.7.1). Полный аудит — не чаще крупной перестройки кода, отчётом `docs/security-audit-<дата>.md`; между полными аудитами делается **повторный проход** — только по изменённому с даты последнего отчёта, в том же формате (найдено / исправлено / принятый риск), с пробным тестом на каждую находку о правах или данных.

Повторный проход обязателен:

- перед **публичным релизом** — по всему изменённому с даты последнего аудита (см. «Ворота публичного релиза» ниже);
- при **новом маршруте без сессии** (`public`, `/health`, `/ready`, что-либо вне `requireAdmin`/`RequireParticipant`);
- при **новом исходящем запросе сервера** на адрес, который задаёт пользователь или админ (почта, push, проверки, вебхуки);
- при **новом секрете** на диске или в БД (ключ, пароль, токен) — включая копирование существующего в новое место (бэкап, экспорт, лог);
- при **новом пути отдачи пользовательских файлов** (блобы, архив, статика, `inline`-отдача);
- при **изменении проверки прав** в `internal/chronicle` (`requireReader`, `requireWriter`, `requireAuthor`, `RequireOwner`, `requireSettingsTx`, `CanAccessBlob` в `internal/blob`) или шлюзов в `internal/api/admin.go`.

Что проверять в проходе — тот же охват, что в отчёте 2026-09-22: таблица маршрутов со шлюзами, каждый публичный маршрут, каждый исходящий запрос, каждый путь отдачи файлов, секреты в БД/файлах/логах. Внешнего аудитора и пентест-инструменты до 1.0 не привлекать.

### Ворота публичного релиза

Первый публичный релиз, кроме обычных ворот (`scripts/test.bat`), требует:

- повторного прохода аудита по всему изменённому с 2026-09-22;
- зеркала на GitHub: репозиторий по адресу `version.SourceURL` существует и совпадает с Gitea (`git ls-remote` обоих remote дают один `HEAD`), теги `vX.Y.Z` отправлены туда же, ссылка на версию в клиенте открывается.

Пока зеркала нет, адрес исходников отвечает 404 — это ожидаемо (см. «Исходники: Gitea и GitHub»).

## CHANGELOG и VERSION

**Журнал изменений — для оператора и участника, не дневник работ.** В корневом `CHANGELOG.md` — только текущая минорная ветка и `Unreleased`; ветки старше лежат в `docs/changelog/0.N.md`. Когда выходит `0.N.0`, вся ветка `0.(N-1).x` переезжает туда тем же коммитом, ссылка добавляется в шапку корневого файла. Архивные записи не переписываются.

Запись версии:

- что изменилось для того, кто держит сервер, и для того, кто им пользуется, — без списков файлов, имён функций и номеров пунктов плана, если без них понятно;
- разделы Keep a Changelog: «Исправлено», «Изменено», «Добавлено», «Удалено»;
- блок **«Оператору»** — обязателен, когда есть что сказать: миграции (номер и что делают с данными), новые или изменённые поля `config.json` и переменные `WYND_*`, требования к прокси, нужен ли бэкап перед обновлением, возможен ли откат.

Версии-пустышки не выпускать: сверка без расхождений, правка одной опечатки в документации, прогон тестов — это не версия. Изменения, которые оператор и участник не заметят (тесты, рефакторинг, документация), копятся под `Unreleased` и уходят с ближайшей настоящей версией.

**Номер версии** — SemVer, до 1.0 минорная цифра растёт при смене поведения, которую стоит объявить (новая возможность, миграция схемы), патч — при исправлениях. Номер живёт в пяти местах и меняется в одном коммите: `VERSION`, `internal/version/version.go` (`Number`), `version` в `web/package.json` и `web/package-lock.json`, `info.version` в `internal/api/openapi-participant.yaml` и `openapi-admin.yaml`. Сторожа — `TestMatchesVERSIONFile` и `TestOpenAPIVersionMatchesVERSION`.

**Ворота.** Коммит, меняющий `VERSION`, допустим только после зелёного `scripts/test.bat` (на Unix — `make test`) на том же дереве. Слово «проверено» в записи без прогона не пишется.

## `.cursor/` и `.claude/`

`.cursor/` лежит в репозитории: это правила и сторож для агентов, которые правят экраны, — не личные настройки редактора.

- `.cursor/rules/wynd-ui-screens.mdc` (`alwaysApply`) — экран собирается только из `$ui` и `$lib/layouts`; не хватает компонента — план «пробел Wynd UI» и стоп; тексты — по голосу продукта.
- `.cursor/hooks.json` вызывает `.cursor/hooks/ui-screens.mjs` до и после каждой записи файла и при остановке агента. Хук — тонкая обёртка над `web/scripts/ui-guard.mjs`, тем же сторожем, что `npm run check:ui`: правило одно, проверяется и в редакторе, и в воротах.

Меняется правило — меняется `ui-guard.mjs` (и его тесты), а текст `.mdc` и `ui-components.md` — тем же коммитом. `.claude/` в `.gitignore`: там локальные настройки запуска, в репозиторий они не идут.
