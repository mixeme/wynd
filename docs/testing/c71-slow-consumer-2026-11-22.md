## Медленный потребитель журнала сборки

Метод: сборка через настоящее ядро (`workshop.Install` → тот же `buildScript` с `tee` в `/var/tmp/wynd-build.log`, что и в окне) с синтетического репозитория на сервере — Dockerfile печатает ~2800 строк по ~1,3 КБ с паузами 0,04 с и завершается `RUN exit 7`, чтобы сборка упала с кодом 1 и журнал остался. Параллельно «потребитель» — отдельный `Wizard` читает журнал настоящим `BuildLogChunk` по рисунку окна: первый вызов — только размер (start = total − хвост 256 КБ), затем порции назад от показанного.

| Что проверено | Итог |
| --- | --- |
| Поток не заторит сборку | Сборка шла 2 м 06 с в собственном темпе (2800 строк × 0,04 с + накладные): канал сборки высасывается горутиной `sess.Run` в кольцевой буфер 256 КБ независимо от окна; кольцо потока — 262 246 байт с пометкой «начало вывода не сохранено» |
| Порции во время роста файла | Порция `[0, 64 181)` взята при total = 798 169 (файл рос); повторное чтение порций, взятых во время сборки, совпало по SHA-256 (0 несовпадений) |
| Целость журнала | Файл на сервере — 2 113 030 байт, sha256 `4e007892…a1df14` |
| Реконструкция из порций | Порции по 256 КБ + остаток до показанного покрывают файл без разрывов; sha256 реконструкции совпал с sha256 файла на сервере |
| Отказ сборки | Экран «Сборка Wynd завершилась с кодом 1» с советом «Повторить» и отсылкой к «Полный вывод сборки» |

Попутно подтверждены защитные отказы того же сценария: нехватка места (`WYND_NO_ROOM` — «На сервере мало места, чтобы собрать Wynd», 3,4 ГБ из нужных 3,5) и отказ сборки по отсутствию `deploy/docker/Dockerfile` в источнике (код 1 за 7 с).

## Найден и исправлен дефект «Загрузить начало»

Первый прогон с большим журналом вскрыл дефект окна: последний шаг спуска просил полные 256 КБ от нуля вместо остатка `[0, start)`. Для журнала 2 113 510 байт (start = 325 625): шаги `[63 481, 325 625)` и `[0, 262 144)` перекрываются на **198 663 байт** — собранное начало дублировало свой хвост в показанном тексте.

Исправлено в main 22.11: арифметика порций вынесена в `cmd/wynd-workshop/frontend/src/lib/buildlog.ts` (`nextLogChunk`), `panel.svelte.ts` использует её; охраняющий тест класса дефекта — `buildlog.test.mjs` (полный спуск без перекрытий для чисел живого прогона, остаток вместо полных 256 КБ, выровненный и малый журнал). Тесты Мастерской 29/29, svelte-check 0/0. Повторный прогон пробника с исправленной математикой: реконструкция из порций совпала с файлом на сервере побайтно.

Вошло в черновик Мастерской 0.4.7; показ в настоящем окне — после установки 0.4.7.

## Дефект SetWindowPos — закрыт миграцией на Wails v3

Наблюдение 08.11 (окно 0.4.1 на Wails v2): «`SetWindowPos` принимается, окно возвращается к сохранённой геометрии» — программный размер не держался, автоматические прогоны не могли задать размер. 22.11 проверено на сборках v3 (`dist/wynd-workshop.exe` и `dist/wynd-signer.exe`, 19.11): `SetWindowPos` задаёт клиентскую область 900 × 700 — размер принят и удерживается (проверки через 0,5 / 2,5 / 7,5 с, возврата нет), стиль окна v3 — обычные `WS_CAPTION|WS_THICKFRAME` со своей отрисовкой рамки. Пробник — `dev/window-resize-probe.py` (окно по pid, размер, контроль возврата). Замечание в [протоколе проверки кадров](ui-review-protocol.md) обновлено.
