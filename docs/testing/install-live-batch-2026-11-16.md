## 1. Копия на работающем сайте и обновление без остановки на время копии (план 45)

Условие ветки: стоящий Wynd 0.52.3 ≥ 0.43.2 (`LiveCopyFrom`, `CanCopyLive`), `StopForCopy=false`, сайт работает. Для проверки прогнан повторный апдейт тем же образом 0.52.3 → 0.52.3 (в окне такой вариант не предлагается, но ядро проходит ту же ветку).

- Порядок шагов в прогоне: **`image` → `copy` → `stop` → `start` → `check`** — копия снята **до** остановки: `docker compose exec -T wynd wynd backup -no-blobs /data/.workshop-copy` на работающем Wynd, затем `stop`, затем запуск и проверка.

- Вывод: ветка «копия на работающем сайте, сайт стоит только на переключение» **подтверждена**; простой — секунды, не минуты копирования.

## 2. Занятый порт при установке (план 45)

- Шаги: `docker`/`place`/`image`/`files` — done; **`start` — failed**: «Порты 80 или 443 на сервере кто-то занял. При осмотре они были свободны. Через них сайт открывается в браузере. Освободите их и нажмите «Повторить».» (ветка `address already in use`/`port is already allocated`; при чужом прокси тот же отказ говорит про 7676).
- Откат с данными убрал пробную установку целиком (контейнер `wynd-port-test-wynd-1` и сеть), стенд не задет.
- **Оценка раннего отказа:** не нужен. При обычном пути окно узнаёт о чужих портах **на осмотре** — с занятыми 80/443/7676 осмотр даёт `block` «На этот сервер Мастерская не поставит Wynd» (чужой веб-сервер). Отказ на «Запуске» — страховка от гонки (порт заняли между осмотром и запуском), текст совета корректен.

## 4. Смена точки монтирования перед удалением (безопасность, план другого каталога)

Условие плана: «изменение ссылки или точки монтирования не должно направить очистку в другую папку». Прогоны на фальшивой установке с подписью «установщик Wynd» в `compose.yaml` и контрольными файлами.

| Сценарий | Что видно откату | Итог |
| --- | --- | --- |
| Базовый: папка с подписью, без монтирования | наш `compose.yaml`, `data/keep.txt` | ✓ откат с данными удалил папку целиком (контрольные файлы ушли) |
| Пустая tmpfs поверх каталога | пустая папка | ✓ отказ **после** выполнения скрипта: `rm -rf` корня → «Device or resource busy», финальная `test ! -e` не прошла; ничего не удалено, исходные файлы под точкой целы. Сообщение об ошибке — весь скрипт целиком («command failed (1): …»), невнятное |
| Чужая непустая tmpfs поверх (файл без подписи) | непустая папка без нашего `compose.yaml` | ✓ повторная проверка каталога отказала **до** изменений; файл-жертва цел |
| **Смонтированная копия нашей установки** (tmpfs с нашим `compose.yaml` и `data/victim.txt`) | наша установка | ✗ **копия стёрта**: `compose.yaml` и `data/` удалены, затем отказ на `test ! -e` («Device or resource busy»); исходные файлы под точкой целы, но **содержимое смонтированной копии уничтожено** |

**Находка.** Перед разрушительным действием ядро не проверяет, что корень — та же самая папка (устройство и inode), что при осмотре. Сценарий «поверх каталога установки смонтирована её копия» (например, примонтировали диск с восстановленной копией, чтобы проверить) приводит к удалению содержимого **смонтированной копии**; отказ приходит уже после удаления и непонятным текстом. Рекомендация: запоминать `dev:ino` корня (при осмотре и в пометке установки) и перед `rm -rf`/очисткой сравнивать, при несовпадении — отказ «каталог изменился (точка монтирования?)»; текст отказа заменить с «command failed» на понятный шаг.
Пункт записан в [план другого каталога](../plans/workshop-install-directory.plan.md). **Исправлено 16–17.11 и проверено живьём** — [протокол неизменности корня](install-root-identity-2026-11-17.md): расхождение `dev:ino` даёт шаг «Каталог установки изменился» до первого изменения, оставшийся каталог — шаг «Каталог установки не удалён».
