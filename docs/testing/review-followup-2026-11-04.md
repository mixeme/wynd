## SEC-03

Коммит: `8006d5fe`.

ZIP ограничен реальной длиной из Range, лимитом оператора (по умолчанию 32 ГиБ), квотой и свободным диском с запасом 64 МиБ. Общая длина сохраняется рядом с частичной загрузкой и не может измениться даже после перезапуска. Перед загрузкой резервируется оставшаяся длина, перед импортом — новые уникальные медиа. Резервы других переносов вычитаются под mutex; после завершения/отказа освобождаются. Внешние процессы и обычные загрузки не используют этот mutex, поэтому фактическое место проверяется повторно; физические ошибки записи также обрабатываются.

Работают максимум два worker, до 24 часов на попытку; разбор/импорт сериализован, ожидание учитывает отмену. Исчерпание места очищает ZIP и запись длины. При истечении исходной ссылки сохраняется прежний принятый префикс для предусмотренного продолжения с новой ссылкой, но резерв фоновой работы освобождается. Совместимость этого сценария подтверждена тестом перезапуска/перевыпуска.

До создания объектов archive/zip ограничиваются и проверяются сам каталог и фактическое число его записей (включая ZIP64). Сумма распакованных медиа ограничена, JSON читается ограниченным потоком: manifest 1 МиБ, одна таблица 16 МиБ, всё JSON 32 МиБ, всего 250000 строк. Строки разбираются с ранней проверкой длины и только примитивными значениями; произвольные вложенные объекты не материализуются как Go maps. Допустимы старые пустые таблицы `rows:null`.

Проверки:

- `TestMoveBudgetUsesActualLengthAndPinsAcrossRestart`: лживая карточка с Bytes=1, фактический total=16 при лимите 8; тело ответа не читается. Изменение длины после перезапуска отклонено.
- `TestMoveReservationsCannotOverbookDisk`, `TestMoveNoRoomStopsBeforeBodyAndReleasesResources`: малый доступный объём, конкуренция резервов, реальный worker; временные файлы и резервы после отказа отсутствуют.
- `TestMoveWorkersHaveCountAndTimeLimits`, `TestMoveImportWaitObservesCancellation`: третья работа отклоняется, первые две заканчиваются по тестовому deadline; очередь импорта учитывает отмену.
- `TestFullArchiveDecompressionBudgets`, `TestFullArchiveDirectoryLimitsBeforeAllocation`, `TestFullArchiveZIP64Directory`, `TestFullTableRejectsNestedCellsAndExcessRows`: сжатая большая строка, общий JSON, manifest/медиа, поддельное число записей, допустимый ZIP64, вложенные объекты и ранняя проверка строк.
- `go test ./internal/config ./internal/archive ./internal/api -run 'Move|ArchivePreservationMove|TestFullArchive(Decompression|Directory|ZIP64)' -count=1` — успешно; после добавления примитивного разбора таблиц повторные archive/API-проверки тоже прошли.
- `go test ./internal/archive -run 'TestFullTable' -fuzz '^FuzzFullArchiveReadLimits$' -fuzztime=10s -parallel=2` — без паник на ограниченном корпусе. Это короткая проверка разбора, не длительный фаззинг.

Нагрузки до исчерпания диска или памяти не было: отказы проверялись на малых искусственных бюджетах. Обычные переносы, A19, докачка после перезапуска и перевыпуска ссылки проходят на том же коде.

Дополнительная приёмка перед выпуском нашла маленький остаток: при замене неактивного черновика удалялся ZIP, но сохранялся новый sidecar `.range`. `TestIncomingReplacementRemovesZIPAndRange` сначала упал именно на оставшемся sidecar ([до](review-followup-2026-11-04/sec03-cleanup-before.log)). Обработчик теперь вызывает общий `removeIncomingFile`, который удаляет оба файла. Регрессия, no_room, реальный перезапуск двух процессов и сохранение префикса после перевыпуска ссылки прошли вместе ([после](review-followup-2026-11-04/sec03-cleanup-after.log)). Подмена исходной ссылки того же снимка с сохранённым ID по-прежнему не удаляет пригодную докачку.

## CODE-03

Коммит: `79a2383e`.

Перед исправлением в мост введены тестовый интерфейс backend и перехват событий без изменения жизненного цикла. На прежней логике три управляемые проверки упали: поздний Fetch(A) заменяет завершившийся B; Sign(A) обнуляет уже заменённый B; отказ B оставляет пригодный A. [Вывод до исправления](review-followup-2026-11-04/code03-before.txt). Порядок задаётся каналами и `testing/synctest`, без задержек и обращения к GitHub или ключам владельца.

Теперь gate принадлежит операции целиком — от начала проверки/подписи до закрытия её ресурса. Начало новой проверки закрывает и сбрасывает прошлую даже при последующем отказе. Backend выдаёт случайный CheckID; подпись сверяет его и тег. У каждого запроса проверки и каждой попытки подписи отдельный RequestID, поэтому даже поздний этап после неправильного пароля не относится к следующей попытке. При закрытии окна контекст отменяется до ожидания и очистки ресурса. Чистая логика идентичности запросов вынесена из Svelte в `release-requests.ts`.

`go test -tags desktop ./cmd/wynd-signer` — успешно: прежние три воспроизведения, повтор того же тега с новым ID, отказ старому ID/чужому тегу, сохранение Check при неправильном пароле и новые ID progress при повторе, отмена Fetch при закрытии. `npm run test` в frontend — **3/3**, поздние ответы/этапы того же тега, повторная подпись, выход из экрана. `npm run check` — 0 ошибок/предупреждений; `npm run build` — успешно. На этой машине CGO=0 и нет C-компилятора: `-race` не запускался; управление порядком проверено синхронными барьерами. Настоящая подпись владельца не выполнялась.

## VAL-01 — аварийные сценарии и повторный проход

Коммит тестов и свидетельств: `b714900c`.

Добавлен `TestMoveLargeArchiveAcrossBothProcessRestarts`: два отдельных процесса сервера, настоящее TCP-соединение, 40 МиБ случайных медиа (больше одного Range-блока), принудительное завершение источника после 1 МиБ и затем получателя после фиксации префикса. Оба процесса запускаются с прежними адресами и каталогами данных. Подтверждены продолжение с `bytes=1048576-`, прежний сильный If-Range, несколько блоков, verified, три записи, SHA-256 всех медиа, принятие на источнике и удаление временного ZIP. В первом полном gate 0.48.2 этот новый тест остановился на ожидании целого 1 МиБ: `Flush` источника подтверждает его socket buffer, а не запись получателем; немедленный Kill/RST может отбросить непрочитанный хвост. Синхронизация уточнена: до Kill дополнительно проверяется фактический размер файла получателя, затем по-прежнему обязательна фиксация префикса в SQLite и перезапуск обоих процессов. Пять последовательных прогонов после изменения прошли, каждый со строго тем же 1 МиБ и SHA-256; тайм-ауты/ожидания не ослаблялись. [Вывод пяти прогонов](review-followup-2026-11-04/val01-process-sync.log). В полном gate остальные Go-пакеты и 451 тест клиента прошли, но весь тот gate считается неуспешным и повторяется после исправлений.

Коммит синхронизации — `f864f9f6`; дополнительная очистка SEC-03 — `edfced03`. Во втором полном gate сценарий процессов прошёл, но Windows не смог удалить SQLite в прежнем `TestMoveStreamKeepsPartialHTTPChunk/changed-representation`: фикстура закрывала DB, не дожидаясь запущенного `notifyCircle` после отмены переноса. В production перед закрытием store уже вызывается `WaitNotify`; такой же порядок добавлен в teardown общей API-фикстуры и перед явным перезапуском/закрытием DB. Ожидание ограничено 10 с и само даёт ошибку теста при незавершении, ошибки очистки не подавляются. Два сценария переноса вместе повторены **8 раз**, все прошли ([вывод](review-followup-2026-11-04/val01-notify-cleanup.log)). Второй полный gate также считается неуспешным; после исправления выполняется новый полный прогон.

`go test ./internal/store ./internal/blob ./internal/backup -run 'SharedContent|Backup|Restore' -count=1 -v` — успешно: миграция 14→15, независимые метаданные/права, общий физический файл, последняя ссылка и конкурирующая публикация, lease, полный и инкрементальный бэкап, запуск восстановленной отдельной копии. На Windows два теста пропущены: POSIX-права и WAL-файл, не созданный в этой среде; они не объявлены пройденными. [Полный вывод](review-followup-2026-11-04/val01-storage.log). Проверка Linux выполняется дополнительно перед развёртыванием.

Производственный алгоритм бэкапа не менялся.

[Вывод](review-followup-2026-11-04/val01-permissions-transfer.log). Проверки гонок управляют конкурирующими операциями, но Go `-race` на локальном CGO=0 не запускался.
