# Проверка кадров перед показом владельцу

Правила действуют также для макетов и картинок в чате, а не только для Svelte-кода. Основа — [AGENTS.md](../../AGENTS.md), [правило экранов](../../.cursor/rules/wynd-ui-screens.mdc) и [Wynd UI](../reference/ui-components.md).

## До изменения

Найти утверждённый исходник и прочитать связанные решения. Записать путь, ID кадра и коммит; перечислить, что именно меняется. Использовать существующие компоненты, сохранить оболочку, шрифты, размеры, интервалы и расположение действий. Не выбирать собственный стиль вместо существующего.

## Перед показом

Получить настоящий снимок изменённого исходника и исходного кадра при одинаковых размерах, теме и масштабе. Проверить сами изображения, затем соответствие снимка исходнику текущего коммита. Только после этого показать нужный кадр владельцу. Если показ идёт по одному кадру, не выдавать согласование первого за принятие остальных.

Ручная перерисовка UI, генеративная картинка или «похожий» экран не заменяют снимок. DOM и тесты подтверждают свои свойства, но не геометрию. Если инструмент не даёт рендер, зафиксировать ограничение без обхода и не предлагать такую картинку на утверждение вёрстки. Это не блокирует независимую работу над логикой.

В записи проверки должны быть:

- основа: путь, кадр, коммит;
- изменение: точный список отличий;
- рендер: инструмент, команда/маршрут, размеры, масштаб и тема;
- изображения: исходный и новый кадр, связь с коммитом исходника;
- результат осмотра и автоматических проверок, их границы;
- ответ владельца: смысл и вёрстка приняты отдельно либо вариант отклонён.

Отсутствующее доказательство не заполнять предположением. Статус снимка «не получен» допустим; статус «визуально проверено» без снимка — нет.

## Снимок работающего окна Мастерской

Проверено 8 ноября 2026. Компьютерный доступ ZCode (дерево доступности) даёт наблюдение и действия по элементам работающего окна, включая скрытое: роли, тексты, нажатия, переключатели, поля. Снимки через этот канал в текущей сборке хелпера Windows не реализованы (нет Windows Graphics Capture) — `getScreenshot` и `include_screenshot` не дают картинку ни для какого окна, ожидать разворота окна бесполезно.

Кадр снимает [capture-workshop-window.ps1](../visual/capture-workshop-window.ps1): PrintWindow с `PW_RENDERFULLCONTENT=2` в PNG, процесс находит по имени либо по pid.

```
powershell -NoProfile -ExecutionPolicy Bypass -File docs/visual/capture-workshop-window.ps1 -OutPath shot.png
```

Известные границы: приложение запоминает геометрию окна, программный `SetWindowPos` игнорируется (работает ручное изменение и `SC_MAXIMIZE`), поэтому кадры сверяют при одинаковом размере окна. Dev-сборка не зарегистрирована как приложение — запускать процесс напрямую (`cmd /c start "" "...\wynd-workshop.exe"`), затем привязываться к окну по pid.

## Автоматическая защита Мастерской

Обычный `npm run check:ui` в `web` и `node docs/visual/check-workshop-servers.mjs` проверяют SHA-256 утверждённого кадра 7в и общих стилей по [реестру основ](../visual/workshop-review-baselines.json). Для C71 сверяют оболочку, выбранный профиль и отсутствие локальной подмены стилей в шапке, навигации и списке серверов. Изменение утверждённой основы требует явного решения об оформлении; новый хеш сам по себе не является утверждением владельца. Проверка включена в штатную команду, а не оставлена отдельным необязательным действием.

Проверка не оценивает красоту, пиксельное соответствие тела экрана или подлинность произвольного PNG. Эти границы нельзя скрывать за зелёным результатом команды. Статусы `draft` и `rejected` означают, что визуальной приёмки нет.

Проверки самого сторожа: `node --test docs/visual/workshop-baseline-guard.test.mjs`. Они проверяют отказ при изменении основы, общих стилей и оболочки, а также запрет объявления вёрстки принятой без записи решения и рендера. Отдельный случай фиксирует границу: изменение тела экрана не превращает черновик в принятый вариант.
