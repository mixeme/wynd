# Холостая сборка архива — бенчмарк, 7 ноября 2026

Первый шаг раздела 8 [плана 60](../plans/60-review-followup.plan.md): измерить, сколько стоит холостая сборка `archive.Size`/`archive.FullSize` ([ревью 6 ноября](../code-review-2026-11-06.md), «Главный кандидат»). Бенчмарк — `internal/archive/size_bench_test.go` (`BenchmarkArchivePass`); выбор способа убрать холостой проход остаётся отдельным решением после этих чисел.

## Что измерено

Холостая сборка (`Size`/`FullSize`) против настоящей (`BuildPersonalArchive`/`BuildFullArchive` в `io.Discard`) на одном и том же круге. Настоящая читает медиа с диска и пишет их в выбрасываемый поток: это стоимость сервера при отдаче без сетевой записи. Данные репрезентативные: настоящие blob-файлы на диске (SSD), кириллический текст записей, по два комментария и реакции, аватары, названия дней; полный архив добавляет те же данные таблицами JSON. Содержимое медиа нулевое — холостой проход его не читает, а CRC32 и заголовки ZIP от байтов не зависят.

Условия: Windows, Intel Core i3-6100U 2,3 ГГц (слабый ноутбучный CPU — числа консервативны), Go 1.27.3, 3–5 итераций на точку. Команда:

```
go test ./internal/archive -run '^$' -bench BenchmarkArchivePass -benchmem [-benchtime 3x]
```

## Выводы

1. **Холостая сборка стоит 40–75 % настоящей.** Отдача архива с точным `Content-Length` сегодня удорожает работу сервера в ~1,4–1,75 раза против чистой сборки: текст сжимается дважды, нули медиа проходят через ZIP-писатель вместе с CRC32.
2. **Абсолютные числа умеренны: ~0,3 с на 1 ГБ архива** на слабом CPU, линейно (~3,5 ГБ/с объёма архива). Гигабайтный архив задерживает первый байт ответа на ~0,3 с; 5 ГБ — на ~1,5 с. Типичный семейный круг (десятки мегабайт) — меньше 10 мс, незаметно.
3. **Память не проблема.** Рост сублинейный: 21–22 МБ распределений на гигабайтном архиве. Опасение ревью про память не подтвердилось; цена холостой — CPU и задержка, не ОЗУ.
4. Малый масштаб (8 МБ) по скорости ниже крупного: доминируют фиксированные расходы (инициализация, мелкие файлы), а не объём медиа.

## Что это значит для трёх вариантов из ревью

Сравнение — следующий шаг, решения пока нет:

- **Арифметический расчёт ZIP-размера** снял бы задержку и ~30–40 % совокупной стоимости отдачи, но должен байт в байт совпадать с Deflate-длиной текстов — равенство придётся доказывать и поддерживать.
- **Поток без `Content-Length`** убирает холостую целиком ценой прогресса и размера скачивания у браузера.
- **Временный файл** точен и даёт `Content-Length`, но тратит место на сервере (важно для маленького VPS и домашнего Pi, C64).

Задержка до первого байта реальна, но ограничена долями секунды на гигабайт; вопрос о том, оправдывает ли она замену механизма, — к владельцу при возвращении к этому пункту.

## Воспроизведение

```
go test ./internal/archive -run '^$' -bench BenchmarkArchivePass -benchmem -benchtime 3x
```

Подготовка пишет ~1,3 ГБ во временный каталог и логирует точные размеры собранных архивов (`-v`). Инвариант точности длины («холостая = настоящая») отдельно закреплён тестом `TestSizeMatchesStreamedArchive`; бенчмарк только измеряет, ничего не утверждает о правильности.
