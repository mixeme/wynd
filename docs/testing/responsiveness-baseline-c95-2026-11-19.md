# Замер отзывчивости C95 — база «до» (2026-11-19)

Задача: C95 плана 46 (отзывчивость при чтении кругов). Владелец согласовал порядок:
сначала замер «до», затем правки по одному кандидату, тот же замер «после»,
сравнение. Телефон OPPO занят разработкой Android — база снята на десктопе;
контрольный проход по OPPO остаётся в плане, когда телефон освободится.

## Метод

- Стенд: сервер `dev/c92/wynd.exe` на 127.0.0.1:7676 (данные `dev/c92/data`),
  dev-клиент vite на 5174 (ветка wails-v3, рабочий каталог).
- Браузер: выделенный Edge (`dev/c95/edge-local`, порт CDP 9223), окно
  412×915 DPR 2, `--disable-backgrounding-occluded-windows` и соседние флаги
  против фоновой приостановки rAF (иначе метки отрисовки не приходят).
- Приближение слабого телефона: `Emulation.setCPUThrottlingRate` ×6.
  Работоспособность проверена бенчмарком в странице: 8 мс → 48 мс.
- Приближение сети до сервера через интернет: второй профиль
  `Network.emulateNetworkConditions` 150 мс RTT / 1,5 Мбит вниз / 0,75 вверх.
- Метки ставит клиент (временная инструментация, в git не пойдёт):
  `web/src/lib/dev/marks.ts` + точки в четырёх экранах (`t:*` — нажатие,
  `d:*` — данные, `r:*` — отрисовано после rAF). После оценки — откатить.
- Драйвер: `dev/c95/measure.mjs <порт> <local|net> [skip-login] [launch]`.
  Сценарий: список → лента, прокрутка до карточки с обсуждением, нажатие →
  запись, «Назад» → восстановление места, «Назад» → список. По 5 повторов;
  первый — холодный (ленивые модули маршрутов dev-клиента), в медиану не
  входит. Запуски (S4) — только в профиле local: vite-клиент не бандлится,
  полная перезагрузка при эмуляции сети была бы нереалистичной.
- Данные «Дачи» досеяны скриптами `dev/c95/seed.mjs`, `dev/c95/avatars.mjs`,
  `dev/c95/more-posts.mjs` (30 записей, 6 с комментариями, обложка, три
  аватара-идентичности). Браферная сессия — anya@example.com.
- Грабли метода: протухший `web/.svelte-kit` давал цикл full-reload посреди
  сценария (вылечено `rm -rf web/.svelte-kit` + перезапуск vite); клики через
  координаты CDP по кнопкам не доходили до обработчиков — в драйвере JS-клик
  по элементу; координатный ввод и метка «отрисовано» — приближения
  (rAF после `tick`), не «настоящий» кадр.

## Числа «до» (медиана повторов 2–5; в скобках холодный 1-й)

| Переход | local (CPU×6) | net (CPU×6 + 150 мс / 1,5 Мбит) |
| --- | --- | --- |
| S3. Список → лента (нажатие по кругу → записи отрисованы) | 455 (924) | 961 (4033) |
| — проверка членства и сведения круга (макет) | 236 | 528 |
| — загрузка ленты и отрисовка | 155 | 386 |
| S1. Нажатие в ленте → текст записи | 222 (287) | 344 (1048) |
| S2. «Назад» → та же карточка на прежнем месте | 312 (144) | 409 (547) |
| S3б. «Назад» → список кругов | 204 (467) | 756 (726) |
| S4. Запуск → строки доступны нажатию (от начала загрузки) | 1215 (среднее пяти: 1117–1674) | не мерился |

По устройствам: числа — для сравнения «до/после», не абсолютные: dev-клиент
не бандлится, SW на dev-стенде нет (реальный запуск включает установку SW),
замедления — приближения к OPPO.

## Что из базы следует

1. **S3, «Список → лента».** Проверка членства и сведения круга (макет
   `[id]/+layout.svelte`, цепочка resolve → circles → цвет → сессия → detail →
   аватар) занимает 236 из 455 мс local и 528 из 961 мс net — больше половины.
   Лента начинается только после макета (feed-load-start ≈ layout-ready).
   Подтверждение кандидата №2: запускать запрос ленты одновременно.
2. **S1, «нажатие → текст» (net).** ~344 мс, почти всё — до данных записи
   (post-data). Экран записи перечитывает всю ленту и ждёт обложки/аватары
   последовательными await до отрисовки (шлюз `loading` до `finally`).
   Подтверждение кандидата №1: открывать текст из загруженного, остальное —
   в фоне.
3. **S2, «Назад».** ~409 мс net: почти всё — перечитывание ленты после
   возврата (restore-start ≈ конец загрузки). Тот же кандидат №1: держать
   загруженную ленту на время чтения.
4. **S3б, «Назад» → список.** ~756 мс net: пересоздание списка — initSession →
   IndexedDB → loadStreet → статус оплаты → отрисовка (строки появляются
   только после оплаты, кандидат №3). Полная правка — вне топ-3 C95, отмечено
   в протоколе.

## Кандидат №1 — «после» (2026-11-19, реализован в тот же день)

Правка: лента круга на время чтения живёт в общем контроллере
`web/src/lib/journal/reading.svelte.ts` (класс `CircleReading`: FeedData + общие
словари обложек и лиц). Экран ленты и экран записи делят его; запись
открывается из загруженного (текст и обсуждение сразу, обложки и лица фоном,
обновление ленты фоном), возврат в ленту не перечитывает её и сразу ставит
карточку на место. Запись снимается при уходе со круга или смене круга
(макет `[id]/+layout.svelte`). `FeedData` получил `rebind` (план 60).
Тесты: `reading.svelte.test.ts` (деление контроллера, перенацеливание
lastRead, сброс при уходе), FeedData-тесты без изменений. Svelte-check чистый.

Числа «после» — те же скрипты и данные; медианы тёплых повторов, local —
пул двух прогонов (8 повторов):

| Переход | local «до» → «после» | net «до» → «после» |
| --- | --- | --- |
| S1. Нажатие → текст записи | 222 → **66** | 344 → **133** |
| S2. «Назад» → карточка на месте | 312 → **94** | 409 → **228** |
| S3. Список → лента | 455 → 310 | 961 → 832 |
| S3б. «Назад» → список | 204 → 191 | 756 → 762 |

S1 и S2 — то, что правил кандидат №1: по сети нажатие → текст быстрее в ~2,6
раза, возврат в ленту — в ~1,8 раза; локально оба перехода ~в 3 раза. Остаток
S2 — пересоздание экрана ленты роутером под замедлением (~230 мс net), без
перечитывания. S3/S3б правка не касалась — в пределах шума прогона; их ведут
кандидаты №2 и №3. Холодный первый прогон S1 (модули маршрута) — 971 мс net.

## Как мерим «после»

Те же скрипты и данные, тот же стенд; для каждого кандидата — прогон
local + net до и после правки, сравнение по медианам. Первый кандидат —
№1 (лента → запись → назад), как в C95. Контрольный сверочный проход на OPPO —
когда телефон освободится.
