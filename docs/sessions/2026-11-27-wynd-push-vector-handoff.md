нас варианты по альтернативной реализации уведомлений?». Код не менялся; первого

## Открыто и дальше

1. **Режим по умолчанию встроенного клиента** — pull («экономно») или FGS
   («мгновенно»). Предложение — pull; FGS — осознанный выбор. Решение за
   владельцем.
2. **Тип FGS для Google Play** — проверить `remoteMessaging`/`specialUse` до
   реализации; если не подходит, мгновенный режим для F-Droid, Play — pull/UP.
3. **Сервер встроенного канала** — журнал `notify_signals`,
   `GET /api/v1/notify/pending?since=`, SSE `/notify/stream?since=`; TTL 24 ч;
   тот же `push.Signal`; тесты.
4. **Android** — pull через WorkManager (уже есть) и/или FGS + SSE;
   переиспользовать `WyndPushService`; кадры настроек до кода.
5. **Живые проверки** — OPPO/realme: экран выключен, перезагрузка, смена сети,
   24 часа, батарея, Doze, убийство процесса; запись в
   [реестр](../testing/pending-device-checks.md).
6. **Мультисерверность** — обязательна, но позже; встроенный клиент обслуживает
   несколько серверов, у UP один активный адрес.
7. **Первый выпуск 0.1** — без изменений: upstream ntfy + форк, по прежнему
   плану.

## Решения

- Принято: 0.1 не меняется; после него — встроенный журнал Wynd, без ntfy и без
  второго приложения.
- Принято: если UP-доставщик уже есть — используем его, второй не ставим;
  Wynd Push предлагаем, а не навязываем.
- Принято: встроенный клиент — журнал Wynd (pull/FGS), не встроенный
  ntfy-клиент.
- Принято: pull и FGS — выбор пользователя; режим по умолчанию ещё открыт
  (предложение — pull).
- Принято: свой Web Push-сервер внутри Wynd не делаем; ntfy остаётся для
  UP/сообщества.
- Принято: FCM — только документальный последний резерв, вне вектора.
- Принято: мультисерверность решаем позже, не приоритет.
- Отклонено: FCM как путь; свой push-сервер сейчас; встроенный ntfy-клиент (H1)
  как основной; принудительная установка Wynd Push при наличии доставщика.
