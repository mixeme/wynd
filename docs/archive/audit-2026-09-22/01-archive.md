# Аудит 01 — экспорт архива круга (план 42, волна 2а)

Область: `internal/archive/*.go`, `internal/api/archive.go`, `internal/chronicle/archive.go` (части, отдающие данные в экспорт и права), `internal/api/blobs.go` (в части, используемой архивом).

## Находки

### Архив целиком собирается в памяти (`bytes.Buffer`), все медиа круга копируются в неё
- Серьёзность: средняя
- Уверенность: подтверждено кодом
- Где: `internal/archive/archive.go:46-47, 71, 113`
- Атакующий: участник (владелец цикла — см. права в `internal/api/archive.go`, уточняется ниже)
- Что: `BuildPersonalArchive` пишет ZIP в `bytes.Buffer`, `io.Copy` каждого blob-файла идёт в память; результат возвращается как `[]byte`. Для круга с гигабайтами фото/видео один запуск сборки занимает столько же ОЗУ, плюс копия при отдаче. Кто может запустить сборку и сколько раз параллельно — см. далее в `internal/api/archive.go`.
- Как воспроизвести: круг с медиа суммарным объёмом > доступной ОЗУ; запустить сборку архива; наблюдать рост RSS процесса / OOM.
- Исправление: писать ZIP во временный файл (`os.CreateTemp`) и отдавать через `http.ServeContent`/`io.Copy`, либо стримить `zip.NewWriter(w)` прямо в `http.ResponseWriter`; ограничить одну сборку на круг одновременно.

### Сборка архива без ограничения параллельности и частоты — любой читатель круга многократно занимает ОЗУ на размер своего среза
- Серьёзность: средняя
- Уверенность: подтверждено кодом
- Где: `internal/api/archive.go:269-336` (`handleArchiveDownload`), `internal/archive/archive.go:46-113`
- Атакующий: участник круга (любой с `requireReader`, в том числе вышедший с доступом), оплаченный
- Что: `GET /circles/{id}/archive/download` доступен каждому читателю круга (шлюз `paid` + `requireReader` внутри `ArchiveSnapshot`), без лимита одновременных сборок на круг/учётку и без rate-limit. Каждый запрос собирает весь ZIP в `bytes.Buffer` и держит его до конца записи ответа; `WriteTimeout` у сервера нет (`cmd/wynd/main.go:153-155`). Участник, открыв N параллельных загрузок и не читая тело, держит N × (объём медиа среза) в памяти процесса — дешёвый отказ обслуживания всего инстанса.
- Как воспроизвести: круг с ~500 МБ медиа до отсечки; участник открывает 10–20 параллельных `GET .../archive/download` с медленным чтением; RSS сервера растёт кратно, до OOM.
- Исправление: сборка во временный файл + `http.ServeContent` (даёт и Range), семафор «одна сборка на учётку/круг» (`409` при повторе) и кэш готового архива на время цикла; либо стрим `zip.NewWriter(w)` без буфера.

### `GET /circles` и `GET /circles/{id}` во время активного цикла выполняют полный снимок архива (N+1 запросов по всем записям до отсечки)
- Серьёзность: средняя
- Уверенность: подтверждено кодом
- Где: `internal/api/archive.go:14-38` (`archiveCycleJSON` → `EstimateArchivePersonal`), `internal/api/circles.go:36`, `internal/api/archive.go:63`, `internal/chronicle/archive.go:301-333, 407-435`
- Атакующий: участник (оплаченный), также просто нагрузка от всех клиентов
- Что: `EstimateArchivePersonal` вызывает `ArchiveSnapshot`, который выбирает все `id` записей до отсечки **без `SnapshotPostLimit`** и для каждой вызывает `loadFeedPost` (≈5 SQL-запросов на запись: `newReadScope` + `loadPostsByIDs` + медиа + комментарии + реакции), затем по одному запросу на каждый blob. Это выполняется при каждом `GET /api/v1/circles` (для каждого круга с циклом) и `GET /api/v1/circles/{id}` — т.е. при каждом старте/синхронизации клиента. Круг с 3000 записей до отсечки → ~15 000 запросов SQLite на один дешёвый GET; участник может гонять его в цикле.
- Как воспроизвести: круг с несколькими тысячами записей до отсечки, активный цикл; замерить время `GET /api/v1/circles` до/после старта цикла; параллельные запросы от одной учётки.
- Исправление: считать статистику одним-двумя агрегирующими запросами (`COUNT`/`SUM` с `sqlVisibleAt`), а не через сборку `FeedPost`; кэшировать результат на учётку/круг до изменения данных; в `ArchiveSnapshot` пакетно строить посты через `buildFeedPosts` со списком id и одним `readScope`.

### Владелец может задать `deadline` в прошлом — цикл сразу «истёк», участники не получают окна на скачивание
- Серьёзность: низкая
- Уверенность: подтверждено кодом
- Где: `internal/chronicle/archive.go:81-83` (`StartArchiveCycle`), `archive.go:229-231` (`MoveDeadline`); проверка при скачивании `internal/api/archive.go:286-289`; purge — `CirclesDueForArchivePurge` `archive.go:487`
- Атакующий: владелец круга против участников
- Что: единственная проверка — `deadline.IsZero()`. Дедлайн в прошлом принимается; `handleArchiveDownload` сразу отвечает 403, а фоновая задача при первом проходе (`!t.After(now)`) стирает содержимое до отсечки. Продуктовое обещание «участники успевают скачать свой срез» обходится владельцем. Владелец и так может удалить круг целиком, поэтому серьёзность низкая; но письма о старте цикла (`sendArchiveCycleStartEmails`) при этом уйдут с уже мёртвой ссылкой.
- Как воспроизвести: `POST /circles/{id}/archive` с `deadline` = вчера; затем `GET .../archive/download` → 403; дождаться фоновой задачи → записи стёрты.
- Исправление: требовать `deadline.After(now.Add(minWindow))` в `StartArchiveCycle` и `MoveDeadline` (например, не меньше 24 ч), возвращать `ErrInvalid`.

### Одна недоступная медиа-запись ломает архив для всех участников
- Серьёзность: низкая
- Уверенность: подтверждено кодом
- Где: `internal/archive/archive.go:57-64`, `internal/blob/serve.go:22-39`, обработка в `internal/api/archive.go:324-327` → `writeDomainError` → 404
- Атакующий: участник (косвенно) / состояние данных
- Что: `addBlob` при `OpenBlob` → `ErrNotFound` (файл отсутствует на диске, статус не `complete`) прерывает сборку целиком; клиент получает `404 not_found` на весь архив, тогда как `EstimateArchivePersonal` такие blob'ы молча пропускает (`addCompleteArchiveBlob`). Расхождение: баннер показывает N файлов, скачивание отвечает 404 без объяснения. Прямого способа участнику создать такое состояние не нашёл (`post_media` ссылается на завершённые blob'ы), но потерянный файл на диске (сбой FS, ручная чистка) блокирует экспорт круга навсегда.
- Как воспроизвести: удалить файл одного blob'а из каталога хранилища; `GET .../archive/download` → 404.
- Исправление: при `ErrNotFound` пропускать blob (как в оценке) и писать в HTML пометку «файл недоступен»; логировать id.

### Ответ различает состояние цикла до проверки членства
- Серьёзность: заметка
- Уверенность: подтверждено кодом
- Где: `internal/api/archive.go:276-289` — `GetArchiveCycle` и проверка дедлайна выполняются до `requireReader` (внутри `ArchiveSnapshot`, строка 294)
- Атакующий: оплаченный участник другого круга, знающий UUID круга
- Что: для чужого круга без цикла или с циклом в пределах дедлайна ответ 404 (нет цикла / нет членства → `ErrNotFound`), а с истёкшим дедлайном — 403. По коду ответа посторонний узнаёт, что у круга активен просроченный цикл. UUID круга угадать нельзя, утечка минимальна.
- Как воспроизвести: два запроса к чужому кругу до и после дедлайна.
- Исправление: вызывать `RequireReader` первым в обработчике.

### `GET /circles/{id}` для исключённого участника отвечает 403 только при активном цикле
- Серьёзность: заметка (несогласованность, не ослабление)
- Уверенность: подтверждено кодом
- Где: `internal/api/archive.go:47-67` (`ListAccountCircles` включает статус `gone`, затем `archiveCycleJSON` → `requireReader` → `ErrForbidden`), сравн. `internal/api/circles.go:36` (ошибка проглатывается)
- Что: без цикла исключённый получает карточку круга (имя, цвет, статус), с циклом — 403. Утечки нет; поведение должно быть одинаковым. Что именно должен видеть `gone` — вопрос аудита прав (другой файл).

### Промежуточные замечания по `internal/archive/archive.go` (не находки)
- HTML: все пользовательские строки (`CircleName`, `CutoffDate`, `AuthorName`, `Body`, `EntryDate`, `Emoji`, `Post.ID`, пути media) проходят через `html.EscapeString` и вставляются внутрь текста или в атрибуты в двойных кавычках (`html.EscapeString` экранирует `"`). Инлайн-`<script>` нет; `<style>` — константа `baseCSS`. `href`/`src` формируются только из серверных значений (`posts/<id>.html`, `media/<blobID><ext>`, префикс `../`), `javascript:`/`data:` неоткуда взять. Имена файлов, MIME, цвета, упоминания, URL пользователя в HTML вообще не выводятся. Ручная конкатенация вместо `html/template`, но контексты простые, экранирование полное.
- ZIP-имена: `media/<blobID><ext>` и `posts/<Post.ID>.html`; `ext` — из фиксированной таблицы по MIME (`.jpg/.png/.gif/.webp/.mp4/.bin`), пользовательское имя файла не используется. Безопасность зависит от того, что `blobID`/`Post.ID` — серверные UUID (проверяется ниже по `internal/chronicle`/`internal/blob`). Дубли исключены картой `mediaNames`.
- `snippet[:60]` (`archive.go:198-199`) режет UTF-8 по байту — может дать битый рун в оглавлении. Не безопасность → волна 7.
- Тест `archive_test.go` покрывает только отсутствующий blob; тестов на экранирование HTML/имён нет. `HasExternalLinks` используется в `internal/chronicle/archive_test.go:116` и `internal/api/acceptance_test.go:407` (проверка отсутствия внешних ссылок).

## Ответы на обязательные вопросы

1. **HTML в архиве.** Ручная конкатенация (`strings.Builder`), не `html/template`, но каждая пользовательская строка проходит `html.EscapeString`: имя круга (`archive.go:166,171,185,191,218`), дата отсечки, `AuthorName` (`237`), `Body` записи (`256`) и комментария (`284`), `EntryDate`, `Emoji` (`294`), `Post.ID` в `href` (`204`). Все атрибуты в двойных кавычках; `EscapeString` экранирует `"`, `'`, `<`, `>`, `&`. `<script>` в архиве нет вообще; `<style>` — константа `baseCSS`. `href`/`src` строятся из серверных значений: `posts/<uuid>.html`, `../index.html`, `media/<uuid>.<ext>`, где `ext` — из фиксированной таблицы по MIME (`extensionForMime`, по умолчанию `.bin`). `javascript:`/`data:` невозможны — пользователь не влияет ни на одну ссылку. Имена файлов пользователя (`OriginalFilename`), MIME, цвет круга, упоминания, URL, названия дней в HTML **не выводятся**. Замечание: обрезка сниппета `snippet[:60]` по байтам (`archive.go:198-199`) может дать некорректный UTF-8 — не безопасность.
2. **Имена в ZIP.** Только `media/<blobID><ext>`, `posts/<postID>.html`, `index.html`. `blobID` и `postID` — серверные UUID (`internal/blob/upload.go:229` `newID()`, `internal/chronicle/content.go:81` `newID()` → `uid.NewID`). Пользовательские имена файлов не используются → `../`, абсолютные пути, `\`, NUL, `CON`/`NUL`/`COM1`, завершающие точка/пробел, длина, unicode-нормализация неприменимы. Дубли исключены картой `mediaNames` (один blob — один файл, повторные ссылки на него в разных записях переиспользуют имя).
3. **Доступ.** Маршрут под `paid` (`server.go:191`): сессия + оплата; членство и отрезок видимости — `requireReader` в `ArchiveSnapshot` (`chronicle/archive.go:306`): статус `gone` → 403, иначе нужен хотя бы один отрезок `CanRead`. Состав архива: записи фильтруются `readScope.canRead(post.CreatedAt)` (`snapshot_feed.go:74`), комментарии и реакции — тем же `scope` (`snapshot_feed.go:60-64`) плюс `filterFeedPostBefore` по отсечке; удалённые записи отсечены `deleted = 0` (`archive.go:311`) и `post.Deleted` (`snapshot_feed.go:71`). Аватары — только лиц, встречающихся в видимом срезе (`IdentityIDsFromFeed`), текущие неудалённые (`erased_at IS NULL`). Тесты `TestArchiveSnapshotsDifferBySpan` и `TestArchiveSnapshotOmitsContentAfterCutoff` подтверждают. Исключённый (`gone`) скачать не может; вышедший с доступом (статус ≠ `gone`, есть `CanRead`) — может, в пределах своих отрезков, это по замыслу (и письма о цикле уходят им же — `CircleMemberEmails`). Пути к файлам на диске — из `blobs.storage_path` через `OpenBlob` (`filepath.Join(s.dir, filepath.FromSlash(rel))`), пользовательский ввод не участвует; `layout` — единственный query-параметр, принимает только `posts`/иное.
4. **Ресурсы.** Полностью в памяти (`bytes.Buffer` → `[]byte`), временных файлов нет (чистить нечего, но и обрыв клиента не освобождает буфер до конца записи). Нет лимита параллельных сборок, нет rate-limit, нет `WriteTimeout`. Запуск цикла — только владелец (`RequireOwner`), повторный старт при незалоченном цикле — `ErrInvalid`. См. две находки средней серьёзности выше.
5. **Заголовки.** `Content-Type: application/zip`, `Content-Disposition: attachment; filename="wynd-archive-<circleID>.zip"` (circleID — UUID из БД, инъекции в заголовок нет; CR/LF `net/http` в любом случае заменяет), `Content-Length`, `X-Content-Type-Options: nosniff` — глобально в `ServeHTTP` (`server.go:195`). Range не поддерживается (`w.Write`, не `ServeContent`) — многогигабайтный архив не докачать после обрыва; не безопасность.

## Проверено, в порядке

- `internal/archive/archive.go` — экранирование всех пользовательских строк, отсутствие инлайн-скриптов, имена ZIP из UUID, детерминированные расширения по MIME.
- `internal/archive/fs.go`, `testexport.go` — тривиальны; `openBlobFile` получает путь только из `OpenBlob`.
- `internal/api/archive.go:189-267` — `StartArchiveCycle`/`MoveCutoff`/`MoveDeadline` защищены `RequireOwner` внутри `chronicle` (`archive.go:75,163,226`); `MoveCutoff` после лока → 403; повторный старт незалоченного цикла → 400.
- `internal/api/archive.go:125-181` (`handleCircleQuota`) — `RequireOwner`, `cutoff_date` идёт параметром в SQL (`FreedBytesBeforeCutoff`), не конкатенацией.
- `internal/chronicle/archive.go:287-298` `LockCutoff` — атомарный `UPDATE ... WHERE cutoff_locked_at IS NULL`, вызывается после успешной сборки любым читателем — по замыслу («после первого скачивания отрезок фиксируется»).
- BLB-3 (purge не снимал `blob_refs`) — исправлено: `dropPostMediaInTx` (`content.go:264-272`) удаляет и `post_media`, и `blob_refs` в той же транзакции.
- `internal/blob/serve.go:22-54` `OpenBlob` — только `status = 'complete'`, путь из `storage_path` под `s.dir`; исполняемые MIME маркируются, но в архив всё равно попадают только фиксированные расширения из `extensionForMime` (SVG/HTML-blob получит `.bin`).
- Ошибки сборки не раскрывают путей на диске: `writeError` → `writeDomainError` отдаёт только код (`not_found`/`internal`), `err.Error()` уходит только в лог.
- `internal/api/blobs.go` архивом не используется (архив читает файлы напрямую через `blob.Store.OpenBlob`).

## Что остаётся на волну 7

- Память: `BuildPersonalArchive` целиком в `bytes.Buffer`; на многогигабайтном круге — OOM. Переход на временный файл/стрим (см. находки 1–2 — там же и семафор).
- Временных файлов сейчас нет; при переходе на файл нужно `defer os.Remove` и чистка «осиротевших» архивов при старте.
- `ArchiveSnapshot` без `SnapshotPostLimit` и с N+1 запросами (`loadFeedPost` на каждую запись) — заменить на пакетный `buildFeedPosts`; `EstimateArchivePersonal` — на агрегирующие SQL-запросы.
- `snippet[:60]` режет UTF-8 по байтам (`archive.go:198`) — резать по рунам.
- Range/докачка: отдавать через `http.ServeContent`.
- Тесты: нет ни одного теста на экранирование HTML (имя с `<script>`, `"` в имени круга), на состав ZIP-имён, на 403 для `gone` и на 404/403 обработчика скачивания.
- Расхождение «оценка пропускает недоступные blob'ы, сборка падает» (находка выше, низкая).
