Аудит безопасности Wynd 0.7.0, 2026-09-22. Область: блобы, загрузки, SPA/статика, `/health`, CORS, админское хранилище.

Итог: критических 0, высоких 0, средних 2 (резервирование квоты пустыми сессиями; архив круга в памяти), низких 5 (Content-Disposition без экранирования; аватар после исключения; `inline` скриншот оплаты с XML; листинг каталогов; кэш медиа в IDB после выхода), заметок 11. ## Находки

### Content-Disposition собирается конкатенацией: кавычка в имени файла ломает заголовок
- Серьёзность: низкая
- Уверенность: подтверждено кодом
- Где: `internal/api/blobs.go:144`, `internal/blob/filename.go:11-24`, `internal/blob/serve.go:40-49`
- Атакующий: участник (загрузивший файл) против другого участника, скачивающего вложение.
- Что: `sanitizeFilename` вырезает только `\x00`–`\x1f` и берёт `filepath.Base`; кавычка `"`, обратная косая `\`, `;`, DEL (0x7f) и не-ASCII остаются. Заголовок формируется как `attachment; filename="` + name + `"` без экранирования. Имя `x.jpg"; filename*=UTF-8''evil.exe` даёт `Content-Disposition: attachment; filename="x.jpg"; filename*=UTF-8''evil.exe"` — браузеры предпочитают `filename*` и сохранят файл как `evil.exe`, хотя в JSON/интерфейсе имя другое. Имя `a\` даёт незакрытую quoted-string. Не-ASCII передаётся сырыми байтами UTF-8 внутри `filename=` (не по RFC 6266, современные браузеры обычно декодируют как UTF-8, но поведение не гарантировано). CR/LF не проходит: `sanitizeFilename` их вырезает, а `net/http` при записи заголовков в любом случае заменяет `\r\n` на пробел — инъекции заголовков нет.
- Как воспроизвести: `POST /api/v1/uploads` с `"filename":"x.jpg\"; filename*=UTF-8''evil.exe"`, завершить, скачать `GET /api/v1/blobs/{id}` и посмотреть заголовок.
- Исправление: собирать заголовок через `mime.FormatMediaType("attachment", map[string]string{"filename": name})` (он экранирует кавычки и для не-ASCII добавляет `filename*`), либо в `sanitizeFilename` заменять `"` и `\` и всё, что не проходит `mime.FormatMediaType`.

### Принудительный octet-stream не покрывает XML-семейство (`text/xml`, `application/xml`, `text/xsl`)
- Серьёзность: заметка
- Уверенность: подтверждено кодом
- Где: `internal/blob/serve.go:56-70`
- Атакующий: участник против участника.
- Что: список «исполняемых» MIME — svg, html, xhtml, js. `application/xml`/`text/xml` с `<?xml-stylesheet?>` или инлайн-XHTML-namespace могут отрисовываться браузером как документ со скриптами. Практический риск сейчас нулевой: `Content-Disposition: attachment` всегда, `nosniff` есть, а клиент показывает файлы через `blob:`-URL с типом ответа. Заметка на случай, если появится `inline`-отдача.
- Как воспроизвести: загрузить с `mime_type: "application/xml"`, проверить, что `Content-Type` не заменён.
- Исправление: добавить `application/xml`, `text/xml`, `text/xsl`, `application/xslt+xml` в `executableExtension`, либо белый список `image/*`(без svg), `video/*`, `audio/*`, `application/pdf`, остальное → octet-stream.

### MIME при загрузке не валидируется по формату — только по длине
- Серьёзность: заметка
- Уверенность: подтверждено кодом
- Где: `internal/blob/upload.go:53-57`, `internal/api/blobs.go:143`
- Атакующий: участник.
- Что: `mime_type` — любая строка до 255 байт (в том числе с пробелами, кириллицей, `<>`), сохраняется в БД, возвращается в JSON и ставится напрямую в `Content-Type`. `net/http` заменяет `\r\n` на пробел, так что инъекции заголовков нет; неверный `Content-Type` не даёт ничего опасного при `attachment`. Sniffing/валидация MIME — вне плана 42, фиксирую как факт.
- Как воспроизвести: `POST /api/v1/uploads` с `"mime_type":"<script>"`.
- Исправление: проверять через `mime.ParseMediaType` и допускать только `type/subtype` без параметров.

### Пустые сессии загрузки резервируют квоту инстанса без передачи байтов
- Серьёзность: средняя
- Уверенность: подтверждено кодом
- Где: `internal/blob/quota.go:118-129, 157-185`, `internal/blob/upload.go:52-94`, `internal/blob/store.go:10`
- Атакующий: любой оплаченный участник.
- Что: после UPL-2 в квоте инстанса учитывается `SUM(expected_size)` по всем открытым `upload_sessions`. Сессия создаётся одним POST без байтов, TTL 24 часа, число сессий не ограничено (это принятое решение плана 42). Значит один участник за `quota/attachment_max_bytes` дешёвых POST-запросов резервирует всю квоту инстанса — все остальные получают `ErrQuotaExceeded` на `POST /uploads` и на `complete` (`upload.go:225`) в течение суток; повторять можно бесконечно. До UPL-2 для того же эффекта надо было реально залить байты. Не предлагаю лимит сессий (закрыто), но резервирование можно считать иначе.
- Как воспроизвести: N раз `POST /api/v1/uploads {"expected_size": <attachment_max_bytes>, "mime_type":"image/jpeg"}` пока не 4xx-квота; другим участником попробовать загрузить 1 байт — квота.
- Исправление: резервировать `received_bytes`, а не `expected_size` (тогда резерв равен реально занятому на диске месту `.part`); либо учитывать `expected_size` только сессий, созданных не раньше чем N минут назад; либо ограничить сумму `expected_size` открытых сессий на одну учётку долей квоты.

### Оракул существования чужой сессии загрузки (403 против 404)
- Серьёзность: заметка
- Уверенность: подтверждено кодом
- Где: `internal/blob/upload.go:109-117`
- Атакующий: участник.
- Что: `loadSession` для несуществующего id отвечает `ErrNotFound`, для чужого — `ErrForbidden`, поэтому HEAD/PUT/complete по чужому id раскрывают факт существования сессии. Id — UUIDv7 с 74 случайными битами, перебор невозможен; практической ценности нет.
- Как воспроизвести: `HEAD /api/v1/uploads/{чужой id}` → 403, `HEAD /api/v1/uploads/{случайный}` → 404.
- Исправление: возвращать `ErrNotFound` в обоих случаях.

### Проигравший параллельный чанк усекает файл под победителем
- Серьёзность: заметка (целостность, только своя сессия)
- Уверенность: подтверждено кодом
- Где: `internal/blob/upload.go:179-190`
- Атакующий: нет (владелец сессии сам себе).
- Что: два параллельных `PUT` с одним `Upload-Offset` оба пишут в `.part`, победитель обновляет `received_bytes`, проигравший при `RowsAffected == 0` делает `f.Truncate(offset)` и стирает уже записанное победителем. `received_bytes` в БД больше длины файла; следующий чанк сеет дыру из нулей, `complete` падает по SHA-256, сессию не спасти (сброса offset нет). Не безопасность — фиксирую как побочный эффект UPL-1.
- Как воспроизвести: два одновременных PUT одного чанка.
- Исправление: в ветке `n == 0` не трогать файл (победитель уже владеет диапазоном), либо брать блокировку сессии на время чанка.

### Аватар автора доступен исключённому участнику и после исключения (свежие аватары)
- Серьёзность: низкая
- Уверенность: подтверждено кодом (SQL), эксплуатация — предположение (нужен id)
- Где: `internal/blob/serve.go:103-114`
- Атакующий: исключённый/вышедший участник круга.
- Что: третья ветка `CanAccessBlob` разрешает аватар, если у учётки есть любой `membership_span` с `can_read=1` в круге личности и `ident.created_at < ms.ended_at`. Проверяется дата создания *личности*, а не `identity_names.effective_at` строки с аватаром. Значит бывший участник, зная `blob_id`, скачает аватар, который автор поставил уже после его исключения. Получить id он может только если какой-то ответ API (снимок ленты, участники) отдаёт ему текущий аватар — это зона другого агента; по SQL сама проверка дырявая.
- Как воспроизвести: A и B в круге, B исключён; A меняет аватар (новая строка `identity_names`); B делает `GET /api/v1/blobs/{новый avatar_blob_id}` → 200.
- Исправление: добавить `AND inm.effective_at < ms.ended_at` (и симметрично `>= ms.started_at` не нужно — историю до вступления читатель видит по дизайну).

### Архив круга собирается целиком в памяти и отдаётся любому читателю без ограничений
- Серьёзность: средняя (DoS)
- Уверенность: подтверждено кодом
- Где: `internal/api/archive.go:269-336`, `internal/archive/archive.go:38-110`
- Атакующий: любой участник круга с активным циклом архивации (или владелец, запустивший цикл в своём круге).
- Что: `BuildPersonalArchive` пишет ZIP со всеми медиа круга в `bytes.Buffer` (deflate каждого файла — ещё и CPU), затем `w.Write(data)`. На круге с несколькими гигабайтами медиа один запрос — несколько гигабайт RSS; параллельные запросы складываются; ограничений по частоте/одновременности нет, кэша нет. Пункт «память на многогигабайтном круге» есть в плане 42 (волна 7), но там он как качество; фиксирую как вектор отказа обслуживания, доступный рядовому участнику одним GET в цикле.
- Как воспроизвести: круг с большим объёмом медиа, владелец запускает цикл; участник в цикле делает 5–10 параллельных `GET /api/v1/circles/{id}/archive/download` — RSS сервера растёт кратно.
- Исправление: стримить ZIP прямо в `http.ResponseWriter` (`zip.NewWriter(w)`, `Store` для уже сжатых медиа, `Content-Length` не ставить) и ограничить одновременные сборки семафором (1–2 на инстанс) плюс одна сборка на учётку.

### Скриншот оплаты отдаётся админу `inline` с MIME, заявленным участником
- Серьёзность: низкая (сейчас неэксплуатируемо)
- Уверенность: подтверждено кодом; эксплуатация — предположение
- Где: `internal/api/admin_pay.go:184-185`, `internal/blob/serve.go:56-70`
- Атакующий: участник (заявитель) против администратора.
- Что: единственный `inline`-путь отдачи. MIME берётся из заявленного при загрузке; svg/html/js/xhtml приводятся к octet-stream, но `text/xml`/`application/xml` — нет, а XML с корнем `<html xmlns="http://www.w3.org/1999/xhtml"><script>…` браузеры рендерят как XHTML со скриптом. Сейчас это безвредно: маршрут защищён только Bearer (`respond.go:184-191`), навигацией открыть нельзя, а админ-клиент показывает файл через `fetch` → `URL.createObjectURL` → `<img>` (`web/src/routes/admin/pay/requests/[id]/+page.svelte:63-70,150-155`), где скрипт не выполняется. Станет дырой, если появится «открыть оригинал» через `blob:`-URL (наследует origin SPA) или cookie-авторизация.
- Как воспроизвести: загрузить XML/XHTML с `mime_type: "application/xml"`, создать заявку, скачать через `GET /api/v1/admin/pay/blob/{id}` — `Content-Type: application/xml`, `Content-Disposition: inline`.
- Исправление: для этого маршрута ставить `attachment` (как везде) или белый список `image/jpeg|png|webp|gif|application/pdf`, всё прочее → `application/octet-stream`; дополнить `executableExtension` XML-типами.

### Оплаченный шлюз не пропускает загрузку скриншота оплаты
- Серьёзность: заметка (функциональная, не безопасность)
- Уверенность: подтверждено кодом
- Где: `internal/api/server.go:148-151, 175`, `internal/api/admin.go:348-361`
- Атакующий: нет.
- Что: `POST /api/v1/pay/requests` намеренно висит на `participant` («чтобы пользователь мог отправить оплату»), но `blob_id` для заявки берётся только через `POST /api/v1/uploads` → `paid(...)`, которое для просроченной подписки отвечает 403 `payment_required`. Клиент (`web/src/lib/queue/queue.ts:121`, `web/src/lib/journal/posts.ts:18`) других путей загрузки не имеет. Просроченный участник не может приложить скриншот. Если это осознанно (заявка без файла?) — `CreatePayRequest` требует непустой `blob_id` (`internal/auth/pay.go:328`).
- Как воспроизвести: учётка с истёкшей подпиской при включённых реквизитах → `POST /api/v1/uploads` → 403.
- Исправление: перевести маршруты `uploads*` на `participant` (квота и владение проверяются в `blob.Store`), либо отдельный узкий маршрут загрузки для оплаты.

### Строка `blobs` в статусе `pending` при сбое между переносом и коммитом остаётся навсегда
- Серьёзность: заметка (учёт квоты)
- Уверенность: подтверждено кодом
- Где: `internal/blob/upload.go:245-276`, `internal/jobs/routine.go:95-101`, `internal/blob/quota.go:118-129`
- Атакующий: нет (аварийный сценарий).
- Что: если процесс упадёт после `INSERT … 'pending'` и `os.Rename`, но до коммита `UPDATE … 'complete'`, останется строка `pending` с файлом на диске. Рутина чистит только `status = 'complete'`, сессия истечёт и удалится (без `.part`, он уже перенесён). `reservedBytes` учитывает `pending` вечно — квота инстанса медленно «утекает». Не безопасность, но связано с UPL-1/UPL-2.
- Как воспроизвести: убить процесс между `os.Rename` и `tx.Commit` (пробный тест с инъекцией ошибки).
- Исправление: в рутине удалять `blobs` со `status = 'pending'` старше суток вместе с файлом.

### Гонка рутины с привязкой аватара/обложки (нет FK)
- Серьёзность: заметка
- Уверенность: подтверждено кодом
- Где: `internal/jobs/routine.go:95-141`, `internal/store/migrations/0001_schema.sql:92-105,127,158`
- Атакующий: нет.
- Что: `post_media`, `pay_requests`, `blob_refs` держат FK на `blobs`, поэтому гонка «рутина выбрала сироту → пользователь привязал → рутина удалила» упирается в отказ FK (BLB-2 учтён). У `identity_names.avatar_blob_id`, `day_covers.blob_id`, `days.cover_blob_id` FK нет: сирота старше суток, который пользователь ставит аватаром ровно в момент рутины, будет удалён вместе с файлом, аватар «повиснет». Окно — миллисекунды, ущерб — своему аватару.
- Как воспроизвести: только инъекцией паузы между выборкой и `DELETE`.
- Исправление: `DELETE FROM blobs WHERE id = ? AND NOT <ReferencedPredicate>` — перепроверять предикат в самом `DELETE`.

### CSP без `script-src`: инлайн-скрипты и любые источники разрешены
- Серьёзность: заметка (осознанное решение, фиксирую)
- Уверенность: подтверждено кодом
- Где: `web/serve.go:69-74`, `web/dist/index.html` (два инлайн `<script>`)
- Атакующий: —
- Что: политика `frame-ancestors 'none'; object-src 'none'; base-uri 'self'` защищает от кликджекинга и `<base>`, но не смягчает XSS: без `script-src` любой инлайновый/внешний скрипт выполняется, без `connect-src`/`form-action` утечка токена из IDB при XSS ничем не ограничена. Комментарий в коде объясняет: клиент ходит на другие origin'ы, поэтому `connect-src` не задают; но `script-src 'self'` + хэши SvelteKit (`kit.csp.mode: 'hash'`) не мешали бы многосерверности. Заголовки на статике и index.html одинаковые (ставятся до ветвления), `Referrer-Policy` есть, HSTS — на прокси (сниппеты `admin_check.go:95,108`).
- Как воспроизвести: `curl -I /` — смотреть `Content-Security-Policy`.
- Исправление: `script-src 'self'` с хэшами через `kit.csp` в `svelte.config.js`; `form-action 'self'`; `connect-src` оставить открытым.

### Кэш медиа и очередь в IndexedDB не очищаются при выходе
- Серьёзность: низкая (клиент, общий компьютер)
- Уверенность: подтверждено кодом
- Где: `web/src/lib/session/session.svelte.ts:65-74`, `web/src/lib/idb/db.ts:494-497`, `web/src/routes/settings/app/+page.svelte:80`
- Атакующий: следующий пользователь того же браузера.
- Что: `dropParticipantSession` удаляет `sessions`, `cursors`, `snapshots` по origin, но не трогает хранилище `media` (`${origin}:${blob_id}` → ArrayBuffer с фото/видео) и `queue` (неотправленные записи с файлами). После выхода расшифрованные медиа остаются в IDB до ручной «очистки кэша» в настройках. Service worker при этом чист: `runtimeCaching: []`, precache только бандла, `navigateFallbackDenylist: [/^\/api/]` — `/api/` и блобы SW не кэширует (`web/vite.config.ts:37-44`, `web/dist/sw.js`).
- Как воспроизвести: войти, открыть ленту с фото, выйти; DevTools → IndexedDB → `media` — записи на месте.
- Исправление: в `dropParticipantSession` вызывать удаление `media` по префиксу `${origin}:` и `queue` по `origin`.

### `/ready` возвращает текст ошибки БД

- Исправление: логировать ошибку, в ответ — только `"unavailable"`.

### Нет `Cache-Control` на ответах с блобами
- Серьёзность: заметка
- Уверенность: подтверждено кодом
- Где: `internal/api/blobs.go:143-148`, `internal/api/admin_pay.go:184-189`
- Атакующий: следующий пользователь общего браузера.
- Что: ответы с приватными файлами идут без `Cache-Control`/`ETag`/`Last-Modified`. Запросы с `Authorization` браузеры кладут в приватный кэш только при явных директивах, а промежуточные кэши — нет; практический риск мал (клиент сам хранит в IDB), но явного `private, no-store` нет. `Range`/`http.ServeContent` не используются — `io.Copy` целиком, `Content-Length` из БД.
- Как воспроизвести: `curl -I -H 'Authorization: Bearer …' /api/v1/blobs/{id}`.
- Исправление: `Cache-Control: private, no-store` на оба маршрута.

### Нет `ReadTimeout`/`WriteTimeout` — медленная загрузка держит соединение бесконечно
- Серьёзность: заметка (принятое решение ради SSE и долгих загрузок)
- Уверенность: подтверждено кодом
- Где: `cmd/wynd/main.go:148-156`
- Атакующий: участник.
- Что: `ReadHeaderTimeout` и `IdleTimeout` есть, но тело `PUT /uploads/{id}` можно лить по байту в минуту — соединение и файловый дескриптор заняты неограниченно; `IdleTimeout` действует только между запросами. Требует учётку; типичный компромисс для чанковых загрузок, но верхней границы на длительность одного чанка нет.
- Как воспроизвести: открыть сессию, `PUT` с `Content-Length: 1048576`, слать по байту раз в 50 с.
- Исправление: `http.NewResponseController(w).SetReadDeadline(time.Now().Add(5*time.Minute))` в `handleUploadChunk`; для SSE — `SetWriteDeadline` не ставить.

## Ответы на вопросы задания (сводно)

1. **Отдача блоба.** `CanAccessBlob` (`internal/blob/serve.go:73-115`): (а) владелец — всегда, в т.ч. исключённый к своим старым блобам и к сиротам до GC; (б) `post_media` → пост не удалён → у читателя есть `membership_span.can_read=1` в круге поста и `p.created_at` внутри отрезка — участник круга A не получит блоб круга B, зная id (нет ни одной ветки без членства); (в) аватар — любой читатель круга личности, для бывших — если личность создана до их выхода (см. находку про `effective_at`). Обложка дня — всегда блоб из `post_media` того же круга (`chronicle/day.go:375-381`, `BlobOnPost`), отдельной ветки не нужно. Скриншот оплаты — владельцу (ветка а) и админу через `/admin/pay/blob`. Аноним → шлюз `paid` → 403 до обработчика. Заголовки: `Content-Type` из БД с принудительным octet-stream для svg/svg+xml/html/xhtml/js (`serve.go:56-70`, тест `TestHTMLBlobNotExecuted`), `image/svg+xml` внутри `image/*` попадает под замену; `Content-Disposition: attachment` всегда (см. находку о кавычках); `nosniff` есть; `Cache-Control`, `Range`, `ServeContent`, `X-Frame-Options` — нет (attachment делает последнее ненужным). Путь на диске — `storage_path` из строки БД (`aa/uuid`), id из URL — только SQL-параметр; `..` из URL до `filepath.Join` не доходит.
2. **Загрузка.** `POST /uploads`: `expected_size > 0`, `≤ attachment_max_bytes`, MIME 1..255 байт (формат не проверяется), квота инстанса с резервом открытых сессий и `pending`-строк (UPL-2 на месте, `quota.go:157-185`); число сессий не ограничено (закрыто планом) — см. находку о резервировании. `PUT`: `loadSession` сверяет `account_id` (`upload.go:115-117`) — в чужую сессию писать нельзя; `offset` должен равняться `received_bytes` (отрицательный/произвольный → 400), `offset ≥ expected` → 400, перелёт читается максимум до `remaining+1 MiB` и усекается (UPL-1); `.part` строится из id только после успешной выборки строки. `RequirePaidParticipantStream` = `RequirePaidParticipant` минус `limitBody`; используется только на `PUT`, который тело читает через `LimitReader`, JSON не парсит — ничего лишнего не пропускает. `HEAD` — только свои сессии (403 на чужие, см. заметку об оракуле). `complete`: SHA-256 обязателен и сверяется, размер = `expected_size`, MIME — заявленный (sniffing вне плана), `rename` с фолбэком на копию, строка `pending` → `complete` в транзакции. Привязка сироты: посты — `ValidateOwnedComplete` (`journal.go:93,489`), аватар — `circle_settings.go:96`, обложка — `BlobOnPost`, оплата — `pay.go:350-362`; все проверяют `blobs.account_id == sess.AccountID`. Чужой сирота непривязываем.
3. **Сирота и GC.** Владельцу доступен по id до удаления рутиной: `status='complete' AND created_at < now-24h AND NOT ReferencedPredicate` (`routine.go:95-101`). Предикат един (`refs.go:19-33`), покрывает `blob_refs`, `post_media`, `day_covers`, `days.cover_blob_id`, `identity_names`, `pay_requests` — BLB-1/BLB-2 исправлены; BLB-3 (purge архива не снимал `blob_refs`) исправлен: `dropPostMediaInTx` удаляет и `post_media`, и `blob_refs` (`chronicle/content.go:264-272`). Сессии старше `expires_at` чистятся вместе с `.part`.
4. **SPA/статика.** Листинг каталогов — есть (находка). Traversal невозможен: `path.Clean` + `embed.FS`/`http.FS` (`fs.ValidPath` отвергает `..`, `\` не разделитель). Заголовки безопасности одинаковы для index.html и статики (`serve.go:18`). CSP — только `frame-ancestors/object-src/base-uri` (заметка). SW: `generateSW`, precache бандла и иконок, `runtimeCaching: []`, `/api` в denylist навигации — ни API, ни блобы SW не кэширует. `/dev/*`: `dev` из `$app/environment` — константа сборки (`import.meta.env.DEV`), в прод-бандле `load()` всегда `error(404)`; код страниц остаётся в `_app/immutable/nodes/*`, секретов в нём нет. `manifest.webmanifest`: имя, иконки, `start_url: "/"`, `scope: "./"` — ничего лишнего. `web/static/`: иконки, шрифты Golos + `OFL.txt` + `README.md` (публично, безвредно).
5. **`/health`** — `{"status":"ok"}`, ничего не раскрывает; `/ready` — см. заметку. Неизвестные `/api/*` → 404 `text/plain` от `http.ServeMux` (API-6, не безопасность), `nosniff` ставится в `Server.ServeHTTP`. `HEAD` на GET-маршрутах обслуживается Go-мультиплексором (тело отбрасывается). `OPTIONS` → 405. **CORS-заголовков нет ни в Go, ни в сниппетах прокси** (`grep Access-Control` — пусто). Следствие: браузерный клиент с origin A не может ходить к API origin B с `Authorization` (preflight провалится) — многосерверность из `client-reference.md:75` работает только через прокси или в не-браузерной среде; это функциональный пробел, не дыра. С точки зрения безопасности отсутствие CORS — самая строгая конфигурация; при добавлении — Bearer без cookie допускает `*` без `credentials`, но `Access-Control-Allow-Credentials: true` с отражённым origin вводить нельзя.
6. **Админское хранилище.** `admin_storage.go` работает только с агрегатами (`SUM`, `COUNT`) и настройками квот; ни чтения файлов по имени/пути, ни удаления сирот по id из запроса нет. `quota_admin.go` — те же агрегаты и `UPDATE circles/quota_requests` по id с проверкой существования. Удаление скриншота оплаты — `RejectPayRequest(id, blobsDir)` по id заявки, файл берётся из БД (`pay.go:557`). Права админа — у другого агента.
