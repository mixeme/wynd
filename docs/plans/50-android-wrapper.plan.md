## Принятые решения

- Цель — поэтапно снять ограничения браузера. Веб-приложение остаётся самостоятельным способом пользоваться Wynd.
- Сначала интерфейс с выбранного сервера. **Уточнение владельца 2026-11-16:** причиной отсрочки вшитого интерфейса была доставка частых обновлений. Следующий шаг — канал APK через GitHub Releases; после проверки канала переходить к вшитому интерфейсу, не ждать окончания частых правок. Смена origin и отсутствие автоматического переноса локальных данных приняты ранее; перенос при переходе отдельно проверить.
- **Разрешённое исключение 2026-11-16:** на вопрос о локальной стартовой части владелец ответил «Да, только стартовые экраны». В APK разрешены адрес сервера, приглашение/QR и недоступность сервера; лента, редактор, настройки и остальной интерфейс остаются серверными. Это разрешение на объём вшивания, а не утверждение новых экранов: сначала адаптация существующего сценария Настольного, настоящий рендер и предварительное утверждение владельцем, затем включение в APK. Отклонённый вариант `22fc7366` этим ответом не восстановлен.
- Java без Capacitor и других каркасов; небольшой файл Kotlin допустим, если этого потребует библиотека. Код — android/ в этом репозитории.
- Пакет mixeme.wynd. Ключ подписи хранит владелец вне репозитория; потеря ключа мешает обновлению того же приложения.
- Минимальная версия Android — самая низкая, которую допускают необходимые библиотеки. Точное значение определить при первой сборке; повышение — когда поддержка старых версий начнёт мешать.
- Сначала APK, магазины позже; сборку без Google держать пригодной для F-Droid.
- Уведомления — UnifiedPush с предусмотренным путём через Google. WebView не даёт Push API, подписка и показ будут нативными.
- Нативный мост доступен только выбранному источнику интерфейса; чужие ссылки открываются в браузере. Страница спрашивает возможности моста и без него работает как в браузере.
- Источник интерфейса видит входы на все серверы и может менять код страницы. Этот довод за вшитый интерфейс не отменил начальное решение загружать с сервера.
- Поиски TWA завершены: это не способ снять ограничения. Повторный выбор Wails — после перехода к вшитому интерфейсу.

### Вшитый интерфейс — по схеме Настольного (решение 23.11)

Владелец 2026-11-23: «По вшиванию интерфейса делаем по той же схеме, как с
Настольным». Схема Настольного — [план 66](66-desktop-functions.plan.md),
функция 9: клиент вшит в сборку, по умолчанию интерфейс по-прежнему приходит
с сервера, вшитый включается отдельным режимом; переключение на вшитый как
основной — после стабилизации интерфейса, отдельным решением, с кадрами и
приёмкой. Origin не меняется, поэтому данные клиента переносить не нужно.

Android-подготовка:

- `web/dist` собирается задачей Gradle и кладётся в assets APK. Сборка с
  клиентом включается свойством `-PwyndEmbeddedUi=true`
  (`BuildConfig.EMBEDDED_UI`); по умолчанию выключено — обычные APK остаются
  прежними и не растут.
- В режиме embedded страницы и статика выбранного сервера отдаются из APK
  (`shouldInterceptRequest`) с SPA-фолбэком; `/api/`, `/health`, `/ready`,
  SSE, медиа, докачка и скачивания идут обычной сетью на сервер. Origin
  остаётся адресом сервера, поэтому сессии, снимки и очередь в IndexedDB
  остаются на месте.
- Сервис-воркер: вшитый `sw.js` встаёт на тот же origin и кэширует вшитый
  клиент; поведение при старом воркере от сервера проверяется живьём.
- Видимый интерфейс не меняется — новые кадры этой подготовкой не
  утверждаются. Переключение по умолчанию (роль «встроенный» в «Настройки →
  Приложение → Интерфейс», откат на серверный, кадры и приёмка) — после
  стабилизации интерфейса, по слову владельца; тогда же решается судьба
  данных при смене режима и подача F-Droid (план 67).

Подготовка сделана 24.11: полный `web/dist` в `assets/www`, каталог `_app`
переложен в `app/` (aapt не пакует каталоги с `_`), одноразовый сброс старого
Service Worker и CacheStorage при смене сборки APK, IndexedDB не трогается.
Ворота и живой прогон на OPPO — [протокол](../testing/android-embedded-ui-2026-11-24.md).

  `47743dab`. В APK 0.1.0 его ещё нет — войдёт в следующий выпуск.
- «Если сервер жив и ты попал на следующий экран, то нельзя вернуться и поменять
  сервер» — **открытый вопрос владельца**: требуются сценарий возврата к смене
  источника после загрузки живого интерфейса (системная «Назад» и путь «Настройки
  → Приложение → Интерфейс» серверной страницы) и утверждение экранов до
  реализации. Не реализовано.

  **Сценарий возвращения — понят владельцем 20.11 окончательно.** Проблема
  первого запуска: чистое приложение → ввод адреса сервера → экран «Войти»
  (почта) → **вернуться к вводу адреса нельзя** (в окне — оболочка под
  iframe не видна, в Android — WebView при подтверждении адреса создаётся
  заново без истории). Решение владельца: «Стрелку назад делаем для обоих
  приложений» — стрелка на экране входа ведёт **к вводу адреса сервера**:
  - Окно: сообщение `wynd:return-to-address` → оболочка показывает свой
    первый экран «Войти в Wynd» с прежним адресом в поле (можно поправить
    опечатку и подтвердить снова). Выбор источника в `servers.json` не
    стирается.
  - Android: операция моста `startup` в `InterfaceBridge` → `showStartup`
    возвращает стартовый экран оболочки; черновик адреса он восстанавливает
    сам (`startup-draft`, `47743dab`).
  - Системная «Назад» в Android на экране входа делает то же самое: страница
    перехватывает `wynd:android-back` и вызывает ту же операцию (оверлеи
    закрываются раньше — общий обработчик). После входа системная «Назад» —
    обычная навигация серверной страницы (C89).
  - В браузере стрелки нет: «Назад» есть у самого браузера. Смена источника
    на живом интерфейсе — «Настройки → Приложение → Сменить сервер
    интерфейса» (каталог/оболочка), как и раньше.

  Оконная часть вошла в черновик **Настольного 0.4.2** (тег `desktop-v0.4.2`,
  CI собран, заголовок окна проверен живьём — [протокол](../testing/release-desktop-2026-11-20b.md)),
  ждёт подписи и публикации владельца. Android-часть (`ae7ff706`, `b8792abd`)

### C22 — «Фото и видео» и координаты на Android

20 ноября владелец уточнил сценарий для кнопок добавления медиа в ленте и
редакторе. При выключенных «Местах со снимков» в круге открывается системная
галерея. При включённых — галерея сама спрашивает согласие, если версия Android

Если «Места со снимков» включены, а галерея этого телефона отдаёт фото без
координат, Wynd предлагает два варианта для «Фото и видео»:

- **Файлы** — получить исходные координаты снимка с разрешения Android через
  «Фото и видео».
- **Галерея** — открывать галерею. Для снимков, которые нужно добавить с

же условиями. Переключатель по умолчанию выключен. Отмена закрывает диалог без
выбора файлов и без записи настройки. Если открыть галерею не удалось и
Android открыл выбор файлов, результаты действия «Галерея» также должны идти
без координат.

### Встроенный канал (записано 24.11, решение о начале не принято)

Владелец 2026-11-24: «Встроенный канал по аналогии с Delta Chat и Simplex запиши
в план». Смысл — приложение Wynd само держит постоянное соединение с сервером
и показывает уведомления, без отдельного приложения-доставщика (ntfy/Sunup)
и без Google. Для обычного пользователя это путь «включил уведомления — ничего
не устанавливал». Сервер доставки — необязательный push-сервер из
[плана 45](45-workshop.plan.md) или собственный канал сервера Wynd.

**Что должно быть:**

- нативная служба приложения с постоянным соединением (WebSocket/SSE) к
  выбранному серверу; foreground service с постоянным уведомлением,
  восстановление после перезапуска и смены сети;
- регистрация устройства/учётной записи на сервере (токен), очередь
  недоставленного и повтор;
- разбор сигнала и показ по правилам `web/static/push-sw.js`; нажатие открывает
  круг или запись на текущем источнике интерфейса;
- несколько входов и серверов: отдельное соединение или мультиплекс; выход
  снимает регистрацию;
- поведение при выключенных уведомлениях, смене сервера интерфейса и выходе.

**Что проверить до решения:**

- как именно держат фон Delta Chat и SimpleX (у них возможны разные пути,
  включая UnifiedPush), чтобы не повторять чужую ошибку;
- собственный WebSocket-хаб в сервере Wynd против ntfy-контейнера из плана 45:
  первый не тянет чужой сервис, но требует кода очереди и переподключений;
  второй даёт готовую доставку, но остаётся отдельным продуктом;
- foreground service type и правила Android 14+, поведение на realme/OPPO,
  расход батареи и постоянное уведомление; политика Google Play для FGS
  (для F-Droid проще);
- чем этот путь отличается от UnifiedPush: другие UP-приложения его не
  используют, это канал только Wynd. Если нужен общий доставщик для всех
  приложений — это форк доставщика (записан ниже), а не встроенный канал.

**Приёмка (когда начнём):** на телефоне без ntfy и без Google-пути включить
уведомления, убить приложение, получить уведомление; после перезагрузки;
при смене сети; два входа на разных серверах; выход снимает регистрацию;
батарея и постоянное уведомление приемлемы. Решение о начале, объёме и сроке —
за владельцем; в этап 4 задним числом не включается.

### Форк доставщика (записано 24.11, решение о начале не принято)

Владелец 2026-11-24: «Запиши в план форк доставщика. Предустановленного адреса
не будет. Wynd просто должен настроить адрес сервера». Речь о втором APK на
базе `ntfy-android` (Apache-2.0), который не несёт адреса в сборке: адрес
сервера уведомлений ему передаёт Wynd. Пользователь адрес не вводит.

**Что должно быть:**

- форк `ntfy-android`: UP-протокол, WebSocket, foreground service, запуск после
  перезагрузки и переподключения уже есть; интерфейс — минимальный (статус,
  текущий адрес, «отключить»), лишние темы/публикация/настройки убраны;
- компонент настройки для Wynd: Activity/Service, защищённый signature-разрешением
  (оба APK подписаны одним ключом) или одноразовым кодом; принимает адрес
  `https://…`, проверяет https и публичный хост по правилам `internal/push`
  (SEC-7) и сохраняет его как `DefaultBaseURL` доставщика;
- Wynd получает адрес из данных сервера Wynd: сервер сообщает адрес своего
  push-сервера (необязательный ntfy из [плана 45](45-workshop.plan.md)) или
  другого настроенного. Если адреса нет — поведение отдельным решением;
  ntfy.sh молча не подставляем;
- после настройки Wynd регистрируется у доставщика и публикует endpoint на
  своём сервере; смена сервера Wynd обновляет адрес; выход снимает подписку;
- сборка, подпись, F-Droid (в первую очередь) и Play по политике FGS;
  обновления форка и слежение за upstream.

**Почему без запечённого адреса.** `TheBlusky/ntfy-android-builder` и ребренды
(`SaitoTech`, `axon`) запекают `app_base_url` в APK; это работает для одного
сервиса, но не даёт Wynd настраивать адрес и ломается при переезде. Нам нужен
параметр настройки, а не константа сборки. `axon` полезен как образец
`axon://pair/...` и provision-файла, но его канал — свой, не UP-доставщик.

**Что проверить до решения:**

- один `DefaultBaseURL` у доставщика: при нескольких входах Wynd на разных
  серверах с разными push-серверами нужен либо общий push-сервер, либо правка
  форка на адрес для каждой регистрации — это отдельное усложнение;
- смена адреса затрагивает все UP-подписки доставщика, не только Wynd:
  снять/перерегистрировать или предупредить;
- защита exported-компонента: чужое приложение не должно перенастроить
  доставщик на свой сервер (образец — `autoPairServerAllowed` в `axon`);
- поведение, если доставщик не установлен, отключён или обновляется;
- второй APK: магазин, подпись, обновления, доверие, постоянное уведомление
  доставщика; поддержка форка и upstream.

**Приёмка (когда начнём):** установить Wynd и доставщик; подключиться к серверу
с push-сервером; включить уведомления — адрес доставщика выставлен без ввода,
endpoint на нужном сервере; убить Wynd, получить уведомление; сменить сервер —
адрес обновился; выход снимает подписку; чужое приложение не может
перенастроить доставщик. Решение о начале, объёме и сроке — за владельцем.

## Кандидаты в этапы (решение владельца 2026-11-12)

- **Чтение архива круга.** Владелец: «Когда будет нативное приложение под Android, можно подумать в нём над функцией чтения архива.» Речь о C73: распакованный читаемый архив из файлового менеджера на Android не показывает вложенные файлы (`content://` не даёт странице подгружать соседние файлы), и чинить компоновку архива не стали. В приложении это решается иначе: оно само открывает файл архива и достаёт медиа из него. Не этап, пока не начата работа по плану; встаёт после этапа 1.

Проверить системный показ и переход по нажатию при закрытом приложении. **22.11 на OPPO с ntfy 1.25.2 ([протокол](../testing/phone-push-unifiedpush-2026-11-22/README.md)):** доставка учётке с двух серверов, замена endpoint, выход, смена источника со снятием прежней регистрации и открытие круга по тапу подтверждены; при остановленном процессе сигнал не догоняется (свойство доставки). Две учётки одновременно: C69 решён 23.11 окончательно — многосерверность остаётся окну для компьютера и приложению Android, в PWA её не будет; в Android многосерверности пока нет (кнопка «Войти на сервер» без настольного моста не показывается) — задача **C123** плана 46. **23–24.11, OPPO, 0.53.6:** C123 пройден ([протокол](../testing/phone-c123-2026-11-23/README.md)) — два входа в одном приложении, оба списка, две подписки UnifiedPush доставляют одновременно; выход с одного сервера гасит уведомления оставшихся (**C126**), смена сервера интерфейса теряет общий вид (**C127**).
- [ ] При первой сборке этапа 4 проверить, нужен ли собственный проект Firebase. В исходном примере не было Google-плагина и ключей, но это не доказательство отсутствия требования.
- [ ] Нарисовать состояние устаревшей нативной оболочки; обновление интерфейса с сервера не обновляет мост.
- [ ] Магазины и схема публикации — после работоспособного APK.

Сведения для этапа 4 по UnifiedPush AND_3.1.0: RFC 8291, тело 1–4096 байт, открытое сообщение до 3993, endpoint RFC 8030 до 1000 байт. Коннектор получает и расшифровывает тело. VAPID-ключ задаётся сервером, токен и подписка выделяются каждой учётной записи отдельно.

По сверке embedded_fcm_distributor 2026-10-15 Wynd с VAPID не требует отдельного шлюза. Библиотека заявляла отсутствие закрытых Google-компонентов. Эти сведения не заменяют проверку при сборке; открытый вопрос Firebase сохранён выше. С доставщиком UnifiedPush, например ntfy, путь через Google не обязателен.

## Среда разработки

Android CI расширен на push в main и pull request при изменениях Android,
значков или workflow. Actions хранит unsigned APK с суммой и отчёты; сборка
не получает прав записи в репозиторий. Черновик и attestation остаются
отдельной задачей только для Android-тега. Публичный выпуск не выполняется.
[Проверка CI](../testing/android-ci-2026-11-16.md).

Условия владельца от 2026-10-14: ставить, когда начнётся разработка оболочки, всё в D:\android-env.

2026-11-16: по поручению владельца установлены официальные Platform Tools 37.0.1;
USB-отладка подтверждена, ADB выполняет команды на OPPO CPH1931 (Android 10, API 29).
[Протокол и повторное подключение](../testing/android-usb-setup-2026-11-16.md).
