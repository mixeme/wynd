## 1. P0 — гонка чанков разрушает загруженные данные (R1)

`internal/blob/upload.go:140-191`: устаревший параллельный чанк откатывает успешно записанный файл (`Truncate`) и делает завершение сессии невозможным.

- [x] Сериализовать запись файла, обновление SQLite и rollback на уровне upload session. Простого удаления `Truncate` недостаточно: конкурирующая запись уже могла изменить содержимое.
- [x] Регрессионный тест управляемого чередования: успешный первый чанк остаётся завершаемым после устаревшего повторного; устаревший чанк отклоняется.

Приёмка: пробник ревью (`successful first chunk must remain completable after stale retry`) проходит; поведение нормальной последовательной загрузки не меняется. Коммит `bb7d6c77`, `TestStaleChunkKeepsUploadCompletable`.

## 2. P0 — последний фрагмент Range удаляет весь архив (R2)

`internal/api/fullarchive.go:558-565,851-887`: `reachedEnd` учитывает только последний диапазон, после чего ссылка удаляется, архив помечается скачанным и стирается.

- [x] Безопасный минимум: удалять архив только после полного `200 OK`; исключить удаление по `206` последнего фрагмента.
- [x] Покрытие диапазонов для ссылки не вводится: удаление только по полному ответу, поэтому непоследовательная докачка безопасна.

Приёмка: `Range: bytes=<size-1>-` отдаёт один байт и не удаляет архив; полное скачивание удаляет. Коммит `efee4b8e`, `TestFullArchiveLastByteRangeKeepsFile`.

## 3. P0 — параллельные запросы обходят квоту (R3)

`internal/api/journal.go:99-146,529-539` и `internal/blob/quota.go:256-289`: проверка и запись не атомарны. Тот же структурный риск у `CheckMediaQuota` и последующего использования blob.

- [x] Атомарная резервация в SQLite до записи; подтверждение или освобождение резервации вместе с операцией. Проверка лимита и увеличение резерва — одно сериализуемое действие. Согласовано с контуром P0 раздела «Рефакторинг» отчёта: единый «оценить → зарезервировать → записать → подтвердить/освободить».
- [x] Регрессионный тест параллельных созданий записей под квотой «ровно на одну».

Приёмка: прогон из ревью (24 одновременных POST при квоте на одну запись) больше не создаёт записей сверх квоты. Коммит `c3e351c8`, миграция 16, `TestConcurrentTextWritesRespectQuota`.

## 4. P1 — стоимость текста и восстановление (R4, R6)

`internal/blob/quota.go:240-245` занижает расход против фактического учёта `internal/chronicle/volume.go:54-91` (R6); `internal/api/revive.go:335-413` проверяет только blob до вставки (R4).

- [x] Единая модель стоимости текста: предварительная оценка совпадает с фактическим учётом (включая имена автора и участника события).
- [x] `ReviveCircle`: до вставки вычислять файлы, записи, комментарии, реакции, события, имена и приветствие; проверять полный объём вместе с атомарной резервацией места из раздела 3.

Приёмка: пробники R4 и R6 проходят; одна запись с точной оценкой укладывается в квоту без переполнения. Коммит `39f8f50b`, `TestTextCostMatchesTriggers`, `TestReviveTextBytesMatchesInsert`, `TestExactTextCostFitsQuota`, `TestReviveCountsArchiveTextAgainstQuota`.

## 5. P1 — выданная ссылка на архив обходит paywall (R5)

## 8. P2 — оптимизация и рефакторинг по мере изменений

- [x] Benchmark холостой сборки архива (`internal/archive/archive.go:52-56,112-128,734-749`, `internal/archive/full.go:109-118`) на репрезентативных данных: `internal/archive/size_bench_test.go` (`BenchmarkArchivePass`), [протокол измерений](../testing/archive-idle-bench-2026-11-07.md). Холостая стоит 40–75 % настоящей сборки (~0,3 с на 1 ГБ архива на слабом CPU, линейно); память сублинейна, опасение ревью про ОЗУ не подтвердилось.
- [x] Сравнить арифметический расчёт ZIP-размера, однопроходную сборку во временный файл и поток без заранее известного `Content-Length` — [протокол и таблица вариантов](../testing/archive-idle-bench-2026-11-07.md). **Решение владельца 2026-11-07: предварительный расчёт размера остаётся.** Временный файл не рассматривается; решение не хранить копии круга ради каждого скачивания (C38) в силе. Холостую сборку платят только потоковые пути (личный архив и «скачать сразу»); готовый полный архив берёт размер из файла без неё. Пересмотр — при кругах в несколько гигабайт или жалобах на медленный старт скачивания.
- [x] Объединение агрегатных запросов проверки квоты — проверено после атомарности раздела 3 по `EXPLAIN QUERY PLAN` и замерам: [протокол](../testing/quota-check-bench-2026-11-07.md), инструменты — `internal/blob/quota_bench_test.go`. **Объединение выигрыша не даёт**: накладной расход на запрос — микросекунды, стоимость в планах. Проверка стоит 37–53 мс (6 тыс. файлов) и 390–420 мс (60 тыс.) на слабом CPU; 73–85 % — `circleUsedBytes` с полным сканом `blobs` в подзапросе медиа комментариев. Кэширование `usedBytes` не вводится.
- [x] Индексы проверки квоты: выигрыш сначала доказан на тех же бенчмарках (засев перебалансирован на восемь кругов — прежний c1 в полсервера скрывал пропорциональность кругу), затем миграция **17** добавила `comments(circle_id)`, частичный `blobs(size_bytes) WHERE pending` и покрывающий `blob_contents(size_bytes)`; индекс ветки GROUP BY планировщик без ANALYZE не берёт — не добавлен. Полные проверки на 60 тыс. файлов: 336–430 мс → 146–172 мс (−49…−61 %); [протокол, сессия 2](../testing/quota-check-bench-2026-11-07.md). Тест миграции — `TestQuotaIndexesMigration`; общие Go-ворота зелёные.
- [ ] Точечный рефакторинг при связанных изменениях: контроллер операций профиля Мастерской с существующими поведенческими тестами как страховкой; вынос логики крупных экранов в TS-контроллеры. Новые Svelte-компоненты вне правил Wynd UI не создаются, утверждённые кадры сохраняются.

Порядок раздела 8 — после измерений и при связанных изменениях; широкая оптимизация без бенчмарков не выполняется. На 2026-11-07 проведены все измерения и решения: холостая сборка архива — сохранить механизм; проверка квоты — объединения нет, вместо него индексы миграции 17 (−49…−61 % на крупном масштабе).
