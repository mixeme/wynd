### A1. Типы API из OpenAPI

Документ: «OpenAPI-спека — для генерации типов в JS»; таблица клиента: «Типы API — OpenAPI → TypeScript, генерация из Go-спеки».
Код: генерации нет с 0.7.3 (DEC-2). `internal/api/openapi-*.yaml` — оглавление маршрутов, типы пишутся руками в `$lib` (`docs/reference/server-reference.md:113`, `client-reference.md:45`).

Генерация из Go-структур честная, но требует перевести 118 из 139 ответов с map-литералов на структуры — ради ошибки, которой в истории не было. stack.html: раздел «API», таблица клиента, строка в отвергнутых; server-reference: условие пересмотра. **Сделано.**

### A2. Транспорт синхронизации

Документ: «`GET /sync?cursor=…` (SSE или long-poll)».
Код: `GET /api/v1/sync` отвечает SSE, NDJSON или JSON-пачкой по заголовку `Accept` (`internal/api/sync.go:36`); long-poll нет. Клиент берёт SSE (`web/src/lib/sync/sync.ts:198`).

**Решение:** режимы NDJSON и JSON-пачкой убраны из кода — ими пользовались только тесты. `/sync` без `text/event-stream` отвечает 406; тесты читают поток хелпером `syncSSE`, тест «три вида совпадают» удалён. Спека, server-reference и stack.html поправлены. **Сделано.**

### A8. Уведомления

Найдено при разборе A5. Сверка чтением кода и спецификаций; живой пробы с push-сервисом не было.

1. **Второй сервер не может доставить пуш — вероятно, сломано по построению.** stack.html (таблица «Пуши»): «Несколько серверов, одна подписка — каждый сервер шлёт на endpoint; клиент агрегирует». Клиент живёт на одном origin, у service worker одна регистрация и одна `PushSubscription`, созданная с VAPID-ключом того сервера, для которого подписка оформлялась первой. Для остальных серверов `subscribePush` берёт ту же подписку (`getSubscription() ?? subscribe(…)`, `web/src/lib/push/push.ts:48`) и отдаёт им endpoint. Каждый инстанс подписывает пуш своим ключом, а push-сервис обязан отвергнуть сообщение, если ключ не совпадает с ключом подписки (RFC 8292, §4.2 — 403). Сервер 403 не распознаёт как протухшую подписку (`isStaleSubscription` — только 404/410, `internal/push/push.go:316`): ошибка в логе на каждый сигнал, подписка остаётся. Итог: пуши приходят только от одного сервера из нескольких.
   - Возможный выход без участия серверов: отдельная регистрация service worker на каждый сервер (своя `scope`, своя подписка со своим ключом). Требует проверки на устройстве.
2. **Android без Google-сервисов.** Web Push в Chrome идёт через FCM — на de-Googled устройстве пушей нет ни в PWA, ни в TWA. В stack.html упомянуто только как повод для UnifiedPush; как ограничение не сказано.
3. **iOS** — пуши только у PWA «на экран Домой» (16.4+). В stack.html сказано, совпадает.
4. **Переподписка при открытии** — есть: `initPush` в корневом layout (`web/src/lib/push/push.ts:68`). Совпадает.
5. **Нативная оболочка пушей не даёт** (см. A5): в Android WebView нет Push API — только FCM или UnifiedPush нативно.

**Решение:** сначала проверить, потом чинить. Задачи (в очередь плана):

- [ ] Воспроизвести п. 1: телефон, два инстанса с разными VAPID-ключами, сессии на обоих; сигнал со второго — дошёл ли, что ответил push-сервис. Запасной путь без телефона — отправка на реальный endpoint FCM чужим ключом.
- [ ] Если подтвердится: подписка на каждый сервер своей регистрацией service worker (отдельная `scope`); 403 от push-сервиса — как протухшая подписка, наравне с 404/410; тест на сервере.
- [ ] После исправления — stack.html, таблица «Пуши»: строка про несколько серверов по факту; строка «Android без Google-сервисов — пушей нет (Web Push в Chrome идёт через FCM); выход — UnifiedPush, не в 0.x».
