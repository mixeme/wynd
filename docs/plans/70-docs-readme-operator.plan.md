# 70 — Чистовая документация: README и руководство оператора

**Тип:** документация.
**Статус:** проект плана, ждёт утверждения владельцем. Решения по составу приняты 2026-11-24; до утверждения существующие документы не переписываются.
**Обновлено:** 2026-11-24.

## Контекст

Корневой `README.md` сейчас — руководство оператора: требования, `install.sh` и Docker, конфигурация, каталог данных, бэкап, восстановление, обновление. Человек, который впервые открывает репозиторий, видит команды установки раньше, чем понимает, что такое Wynd и зачем ему круг.

Презентация продукта есть в `docs/about.html` («Журнал для своих») и `docs/wynd.html` (образ продукта: термины, голос, отличия, механика), но это HTML-файлы. GitHub и Gitea показывают их как исходник, а не как страницу; GitHub Pages в репозитории не настроен. Опираться на них как на витрину нельзя.

Отдельного плана документации нет. План 43 — только расхождения документов и кода; пункт A3 (установка одной командой) остаётся отложенным.

Цель — два чистых документа: README как презентация продукта для участника и владельца сервера, и `docs/OPERATOR.md` как руководство для того, кто ставит и обслуживает инстанс. Остальные документы остаются источниками и справочниками.

## Принятые решения 2026-11-24

- **Читатель README:** участник круга и владелец сервера. Первый экран — о продукте; ниже два пути: «я в круге» и «я ставлю сервер».
- **Экосистема программ:** README показывает не только веб-приложение, а весь набор: PWA, Android, «Wynd Настольный», «Wynd Мастерская»; работа с архивами — часть Мастерской, а не отдельная программа. У каждой программы — назначение, платформа и честный статус доступности; Linux-сборки и черновики не описываются как готовые.
- **«Wynd Подпись»:** в README есть короткая строка для разработчиков: это инструмент подписи выпусков, не программа для участников и не часть сервера; ссылка на `DEVELOPMENT.md`. Чтобы её не принимали за пользовательскую программу, она названа явно.
- **Техническая часть нынешнего README** переезжает в `docs/OPERATOR.md`; корневой `README.md` становится презентацией. Установочные команды в README не дублируются.
- **Снимки:** 3–5 ключевых экранов, снятых с работающего приложения по правилам проекта. Ручные эскизы, Pillow/canvas/SVG и генеративные изображения вместо снимков не используются.
- **Главный путь установки в руководстве оператора:** «Wynd Мастерская» (сейчас Windows; Linux-сборка — только после отдельного выпуска, заранее не обещать; SSH, установка через Docker, Debian/Ubuntu). Docker вручную и `install.sh` со systemd — ниже как альтернативы.
- **`about.html` и `wynd.html`** остаются в репозитории как расширенные материалы и источники. README не зависит от них: основной рассказ — в самом README. Ссылка на `about.html` — только как на файл для локального просмотра, не как на страницу.
- **Язык и формат:** русский, Markdown. Английская версия и отдельный сайт в этот план не входят.
- **Границы обещаний:** установку одной командой не обещаем; неопубликованные возможности не описываем как доступные. Версия — по файлу `VERSION` и странице выпусков, без преждевременных номеров.

## Что делаем

### 1. README — презентация продукта

Состав:

1. **Начало.** Название, одна фраза о продукте, для кого. Сразу понятно: закрытые круги с общим журналом, без общей ленты, на сервере человека, которого вы знаете.
2. **Что такое Wynd.** Круг — закрытая группа со своим журналом: семья, друзья, коллеги. В круг попадают по ссылке от того, кто уже в нём. Один человек ставит сервер, остальные открывают приложение в браузере телефона.
3. **Как это устроено.** Дни, сетка, карта, поиск; окно правок; удаление; уход не стирает сказанное; круг из одного — дневник. Коротко, без технических подробностей.
4. **Чем отличается.** Нет общей ленты, подписчиков, рекомендаций и рекламы. Серверы не знают друг о друге. Своё можно забрать. Видно то, что вы застали.
5. **Экраны.** 3–5 настоящих снимков с подписями: журнал по дням, сетка или карта, запись, приглашение; при необходимости — окно Мастерской для пути владельца.
6. **Экосистема Wynd.** Один сервер — несколько программ; у каждой своё назначение:
   - **PWA** — веб-приложение, которое открывается в браузере телефона или компьютера и ставится на экран;
   - **Android** — приложение для телефона;
   - **«Wynd Настольный»** — окно для компьютера: трей, уведомления, автозапуск;
   - **«Wynd Мастерская»** — установка и обслуживание сервера владельцем: обновление, откат, бэкап, переезд; работа с архивами — объединить архивы, разделить по годам или периоду, открыть ленту из полного архива круга.
   Таблица «программа — платформа — для кого — что даёт». Статусы — по странице выпусков; Linux-сборки и черновики не выдаются за готовые. Участнику — PWA, Android и Настольный; владельцу — ещё и Мастерская с архивами.
7. **Как начать.** Два пути:
   - **Я в круге.** Ссылка или QR от участника, вход по коду из письма, установка приложения на экран телефона; что человек увидит дальше.
   - **Я ставлю сервер.** Один человек, домен, VPS, SMTP; Мастерская ставит и обслуживает Wynd; ссылка на `docs/OPERATOR.md`.
8. **Документация.** Оператор, архитектура, разработка, безопасность, изменения. Без длинной таблицы всех внутренних файлов.
9. **Разработчикам.** «Wynd Подпись» (`cmd/wynd-signer`) и служебная подпись выпусков Мастерской (`cmd/workshop-sign`) — инструменты разработчика, не программы для участников и не часть сервера; сборка и порядок — в `DEVELOPMENT.md`. Коротко, чтобы их не принимали за пользовательские программы.
10. **Конец.** Лицензия AGPL, исходный код, версия.

Ограничения: без установочных команд, без внутренних терминов и имён механизмов, без адресов чужих серверов и личных данных; голос — «вы», нейтрально.

### 2. `docs/OPERATOR.md` — руководство оператора

Состав:

1. **Кому это руководство.** Оператор — тот, кто поставил сервер и отвечает за него. Один процесс на каталог данных; чужие сервисы не трогаем.
2. **Что нужно.** Debian/Ubuntu VPS, домен и DNS, TLS, SMTP-релей, SSH-доступ, порты 80/443, место на диске, точное время. Для Мастерской — Windows (Linux — после отдельного выпуска); для ручного пути — Docker или systemd.
3. **Быстрый старт: Мастерская.** Скачать и запустить, добавить сервер, отпечаток хоста, осмотр, план «поставим / изменим с копией / не тронем», установка через Docker, выбор прокси (свой Caddy или найденные nginx/Apache/Caddy), домен и сертификат, ссылка первого запуска.
4. **Первый запуск и панель.** Токен первого запуска, пароль панели, имя инстанса, SMTP и проверочное письмо, режим регистрации, квоты, уведомления, архивы и очистка.
5. **Docker вручную.** `compose.yaml`, права на каталог данных (`100:101`), Caddy, `WYND_PUBLIC_URL`, вариант с чужим прокси, шаблоны nginx/Apache/Traefik, таймаут чтения не меньше 300 с, доверенные прокси.
6. **systemd и `install.sh`.** Команда, что создаёт скрипт (пользователь `wynd`, `/var/lib/wynd`, юнит, Caddy), `--own-proxy`, ссылка первого запуска, обновление тем же скриптом.
7. **Настройки.** Три слоя: умолчания → `config.json` → переменные окружения. Таблица основных переменных; полный список — в справочнике сервера. Профиль loopback и проверка `public_url`.
8. **Каталог данных.** `wynd.db` (в нём пароль SMTP и приватный ключ VAPID открытым текстом), `config.json`, `blobs/`, `tmp/`, `keys/`, `backups/`, `dev-auth-codes.log`; права и что не входит в бэкап.
9. **Бэкап.** `wynd backup`, `-incremental`, `VACUUM INTO`, состав каталога, секреты, запуск от пользователя сервиса, Docker.
10. **Восстановление.** Остановка, отложить текущий каталог, разложить копию, права, запуск, проверка; что теряется и что будет с сессиями и курсорами клиентов.
11. **Обновление и откат.** Блоки «Оператору» в CHANGELOG, `install.sh` с копией перед заменой, Docker, миграции при старте, старые версии в несколько шагов, отсутствие отката после миграции.
12. **Диагностика.** Журнал, `/ready`, версия схемы, порты, прокси, SMTP, уведомления, сертификаты и продление, место на диске, состояние бэкапа; частые ошибки и что делать.
13. **Безопасность.** Секреты в базе, права файлов, публичный адрес, loopback, доверенные прокси, TLS, смена пароля панели, сообщение об уязвимости — ссылка на `SECURITY.md`.
14. **Дальше.** Архитектура, справочник сервера, разработка, изменения.

Ограничения: каждая команда и путь сверяются с текущим кодом и скриптами; названия кнопок и полей — с существующим интерфейсом; секреты и реальные адреса в документ не попадают.

### 3. Снимки для README

- Кандидаты: журнал по дням, сетка или карта, экран записи, приглашение по ссылке/QR; одна программа экосистемы — окно «Wynd Настольный» или Мастерской, при необходимости — вкладка архивов Мастерской.
- Съёмка — с настоящего локального сервера с обезличенными данными, в светлой теме, в размере экрана телефона (например, 390×844) или в окне с `PhoneFrame`; одинаковый размер и тема для всех кадров; без чужих имён, адресов и переписок.
- Хранение — `docs/visual/readme/`; при необходимости отдельный скрипт съёмки рядом с существующими инструментами.
- Перед вставкой осмотреть снимки: шапка, навигация, типографика, интервалы, переносы, основные действия. Если настоящий рендер недоступен, снимки не заменяются рисунком — лучше обойтись ссылкой на галерею или без изображений.

## Проверка

- README читается как презентация: человек без технического контекста понимает, что такое Wynd и что делать дальше.
- Руководство оператора проходит путь от чистого сервера до первой записи; команды совпадают с кодом и скриптами.
- Нет противоречий с `ARCHITECTURE.md`, `DEVELOPMENT.md`, `SECURITY.md` и справочниками; нет обещаний неопубликованных возможностей.
- Статусы программ сверены со страницей выпусков на день написания: опубликованы Android 0.1.1, «Настольный» 0.4.3, «Мастерская» 0.4.7; черновики 0.1.2, 0.4.4/0.4.5 и 0.4.8 не описаны как доступные.
- «Архивы» описаны как функция Мастерской, а не отдельная программа; «Wynd Подпись» и `cmd/workshop-sign` названы инструментами разработчика и не выдаются за пользовательские программы.
- Ссылки относительные и работают в GitHub/Gitea; HTML-файлы не выдаются за рендерящиеся страницы.
- В документах нет секретов, личных данных и реальных адресов.
- Полный проход установки на чистом VPS — отдельная живая проверка владельца; в этом плане Docker-путь проверяется локально, ручной — по скриптам и существующим протоколам.

## Порядок работ и коммиты

1. Этот план и строка в `ROADMAP.md`.
2. Снимки и, если нужен, скрипт съёмки.
3. Новый `README.md`.
4. Новый `docs/OPERATOR.md`.
5. Правка ссылок и финальная сверка.
6. Передача в `docs/sessions/`.

Каждый шаг — отдельный коммит только со своими путями. Незавершённые снимки и черновики в main не попадают.

## Не входит

- Переписывание `ARCHITECTURE.md`, `DEVELOPMENT.md`, `SECURITY.md` и справочников.
- Английская версия, отдельный сайт, GitHub Pages.
- Новые возможности продукта и правки интерфейса.
- Установка одной командой (пункт A3 плана 43).
- Изменение выпусков, тегов и версий.

## Открыто

- Какие именно экраны попадут в README — решается после съёмки; окончательный набор показывает владелец.
- Если для владельца нужна отдельная страница «поставить сервер», README даёт короткий путь и ссылку, а подробности остаются в `docs/OPERATOR.md`; отдельный документ не заводится без запроса.
