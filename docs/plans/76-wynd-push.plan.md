# 76 — Wynd Push: сервер уведомлений и доставщик

**Тип:** новая задача (владелец 26.11.2026: «Составляем план для Wynd Push. Серверная часть + доставщик»).
**Статус:** владелец согласовал [кадр шага установки «Сервер уведомлений»](../visual/reviews/wynd-push-install-2026-11-28/README.md). По его замечанию зазоры измерены и приведены к лесенке C120. Дальше кадры пульта и поля хранения. Первый этап — сервер, второй — доставщик. 27.11 записан вектор после первого выпуска: встроенный журнал Wynd без второго приложения, UP — по наличию доставщика.
**Обновлено:** 2026-11-28.

## Решения владельца (26.11)

1. **Основа — ntfy под капотом (вариант А).** Свой сервер, свой протокол и гибрид рассматриваем позже, отдельным решением.
2. **Доставщик — форк `ntfy-android`.** Форк остаётся **общим UnifiedPush-доставщиком**: им могут пользоваться и другие UP-приложения, не только Wynd.
3. **Адрес push-сервера сообщает сервер Wynd.** Адрес хранится в настройках установки, Мастерская заполняет его при установке; клиент получает адрес вместе с данными сервера при входе.
4. **Доставщик ведёт список адресов.** Активен один адрес. Новый адрес добавляется в список, пользователь получает вопрос «переключиться?». Разные адреса одновременно для разных подписок (мультисервер) — позже.
5. **Установка только через Мастерскую.** Ручной Compose и отдельный установщик не делаем; обновление и удаление сервера уведомлений — тоже Мастерская.
6. **Сервер — upstream-образ ntfy.** Свой образ — позже, когда будет понятно, что он даёт.
7. **Режим закрытый.** `auth-default-access: deny-all`; анонимно разрешены только UP-темы `up*` (чтение и запись). Публичной регистрации нет, веб-интерфейс снаружи не показываем. Другие UP-приложения при этом работают.
8. **Сначала сервер, доставщик — вторым шагом.**
9. **Названия:** приложение на телефоне — «Wynd Push»; в Мастерской — и «Сервер уведомлений», и «Wynd Push».
10. **Рабочие подписки не ломаем.** У кого уведомления уже работают через внешний доставщик, тому ничего не анонсируем и не переключаем. Wynd Push предлагаем только новым пользователям.
11. **Новый пользователь — «умный выбор» доставщика.** Если Wynd Push установлен — используем его; если установлен другой UP-доставщик — показываем выбор с пометкой «рекомендуем Wynd Push»; если нет ничего — кнопка установки Wynd Push и вторичная ссылка на список других доставщиков.
12. **Публикация — там же, где Wynd:** GitHub Releases и Google Play; F-Droid — когда там появится основной Wynd (план 67). Отдельную подачу в F-Droid до этого не делаем.
13. **Форк живёт в отдельном репозитории** `wynd-push-android` (Apache-2.0, история upstream, зеркало GitHub). В основном репозитории — только контракт и ссылки.
14. **Имя пакета** — `mixeme.wynd.push`, отдельная подпись в «Подписи» (подтверждено 26.11 вместе с остальными пунктами плана).
15. **Самообновление делаем сразу.** GitHub-сборка Wynd Push обновляется сама из своих релизов; Play-сборка обновляется магазином (правила Play); F-Droid — позже. Выдержку не вводим, как у Wynd до 1.0.0.
16. **Кэш сообщений настраивает админ.** Не фиксированные 12 ч, а поле в пульте Мастерской; значение по умолчанию — 12 ч.

## Что не входит в первый выпуск

- Свой push-сервер, свой образ ntfy или гибрид с сервером Wynd — отдельные решения после первого выпуска.
- Авторизация и токены на публикацию/подписку, открытая регистрация, веб-интерфейс ntfy.
- Одновременная работа нескольких push-серверов на одном телефоне (мультисервер).
- Автоматическое переключение или анонс для существующих рабочих подписок.
- Ручная установка push-сервера, внешний push-сервер, установка без Мастерской.
- Изменения PWA/браузерного Web Push, Настольного приложения, iOS.
- Подача Wynd Push в F-Droid до появления основного Wynd.

## Архитектура

### Сервер в установке

- **Необязательный шаг Мастерской.** Установки без шага не меняются. Шаг появляется и в установке, и в пульте; удаление — только своего сервера уведомлений.
- **Отдельный Compose-файл `push.yaml`.** Основной `compose.yaml` не меняется. При включённом шаге в `.env` установки добавляется `COMPOSE_FILE=compose.yaml:push.yaml` (Docker Compose читает его из `.env`). В `push.yaml` — сервис `push` (образ ntfy, закреплённая версия), конфиг `ntfy.yml`, окружение `WYND_PUSH_SERVER=https://push.<домен>` для сервиса `wynd`, `restart: unless-stopped`. Тома нет: кэш сообщений эфемерный, вложений нет.
- **Настройки шага — `push.json`.** В каталоге установки: домен и срок кэша; `push.yaml` и `ntfy.yml` — производные от него. Пульт читает и пишет `push.json`; обновление и откат его сохраняют; удаление удаляет вместе с сервисом. Секретов в файле нет.
- **Поддомен и сертификат.** Мастерская спрашивает поддомен (например, `push.example.org`), проверяет, что DNS уже указывает на сервер, и добавляет сайт в `Caddyfile`:
  `push.example.org { reverse_proxy push:80 }`. Сертификат выпускает Caddy Мастерской. Основной сайт не меняется.
- **Здоровье.** Мастерская проверяет `https://push.<домен>/v1/health`; в пульте — состояние «Сервер уведомлений работает / не отвечает» и версия образа.
- **Обновление и откат.** `push.yaml`, `COMPOSE_FILE` и блок Caddy сохраняются при обновлении и откате; при удалении удаляются только свои файлы и блок, затем `docker compose up -d --remove-orphans`. Чужие контейнеры, тома и сертификаты не трогаются.
- **Адрес для Wynd.** Мастерская пишет `WYND_PUSH_SERVER` в окружение сервиса `wynd` в `push.yaml`. `internal/config` читает переменную; `/api/v1/instance` отдаёт `push_server`. Если переменной нет — поля нет. Адрес проверяется: только `https`, публичный хост, без пути и параметров; хвостовой `/` отбрасывается. Неверный адрес пишется в журнал и не отдаётся клиенту.
- **Кэш настраивает админ.** В пульте Мастерской — поле «Хранить сообщения»: «не хранить», 1 ч, 6 ч, 12 ч (по умолчанию), 24 ч, 3 дня. Значение пишется в `push.json` и `ntfy.yml` (`cache-duration`), сервис `push` перезапускается, здоровье проверяется заново. Перезапуск очищает эфемерный кэш — предупредить в подсказке поля. Значение переживает обновление и откат.
- **Почему override, а не правка основного Compose.** Установки без шага остаются байт-в-байт прежними, тесты `ComposeFile`/`deploy/docker/compose.yaml` не ломаются, а удаление шага — это удаление своего файла, а не вырезание сервиса из общего файла.

### Настройка ntfy

Файл `ntfy.yml` монтируется в контейнер только для чтения. Закрытый режим:

- `base-url: https://push.<домен>`, `listen-http: :80`, `behind-proxy: true`.
- `cache-duration` — значение из настроек админа, по умолчанию `12h` (сообщения эфемерные; телефон догоняет после подключения).
- `auth-default-access: deny-all`.
- `auth-access: ["*:up*:rw"]` — анонимное чтение нужно нашему доставщику, запись — серверам чужих UP-приложений. Это единственное исключение.
- Публичная регистрация выключена; веб-корень выключен; вложения выключены; метрики выключены.
- `visitor-subscriber-rate-limiting: true` — защита от публикации в тему без подписчика (507/410, как на ntfy.sh).
- Точные ключи конфигурации сверить с выбранной версией образа; проверка — отдельным стендом (см. этап 1, шаг 3). Версия образа фиксируется в `push.yaml` и протоколе, не `latest`.

### Доставщик

- Отдельный репозиторий `wynd-push-android`, форк `ntfy-android` с закреплённого тега, Apache-2.0 и NOTICE сохраняются. Приложение — «Wynd Push», пакет `mixeme.wynd.push`, без Firebase-сборки.
- **Запечённого адреса нет.** На свежей установке сервер не выбран; адрес приходит от Wynd. Ручное добавление сервера остаётся — форк общий UP-доставщик, им пользуются и другие приложения.
- **Список адресов.** В настройках — список известных push-серверов и активный. Новый адрес от Wynd добавляется в список; если он не активен, Wynd спрашивает «Переключить доставку на <хост>?». Переключение меняет `DefaultBaseURL` доставщика, перерегистрирует все UP-подписки (не только Wynd) и предупреждает об этом.
- **Защищённый контракт.** Настройка из Wynd — через exported Activity подтверждения в доставщике (или bound service с пользовательским подтверждением): Wynd передаёт адрес, доставщик показывает «Wynd просит использовать сервер <хост>» и меняет настройку только после нажатия. `protectionLevel="signature"` не годится как основной путь: Google Play и F-Droid переподписывают приложения своими ключами, поэтому подписи Wynd и Wynd Push в магазинных сборках разные. Подтверждение работает в любом канале; чужое приложение может лишь открыть диалог, но не перенастроить доставщик молча. Список адресов и активный выбор читаются через тот же контракт; адрес проверяется внутри доставщика (https, публичный хост, длина).
- **Самообновление — сразу, но по каналам.** GitHub-сборка (`standard`) обновляется сама из релизов `wynd-push-android`: проверка versionCode, подписи APK (закреплённый сертификат) и хеша ассета, затем установка через FileProvider; выдержки нет, как у Wynd до 1.0.0. Play-сборка без `REQUEST_INSTALL_PACKAGES` и без самообновления — обновляет магазин; F-Droid собирает сам. Код обновления Wynd (AGPL) в форк не копируем, чтобы сохранить Apache-2.0: реализация своя, по тому же контракту. Строка «Вышла версия …» и экран обновления — новые кадры до кода.
- **Новый пользователь в Wynd.** При включении уведомлений Wynd читает `push_server` из `/api/v1/instance` и действует по «умному выбору»: Wynd Push установлен → используем; другой UP-доставщик → выбор с рекомендацией; ничего нет → установка Wynd Push и вторичная ссылка на список UP-доставщиков. Без `push_server` — не подставляем ntfy.sh молча, показываем подсказку и оставляем внешние доставщики.
- **Существующие подписки не трогаем.** Если у учётной записи на этом устройстве уже есть рабочая подписка, новый адрес не передаём, ничего не анонсируем и не перерегистрируем. «Новый» — тот, кто включает уведомления впервые.

## Этап 1 — сервер

### Шаг 1. Сервер сообщает адрес

- `internal/config`: переменная `WYND_PUSH_SERVER`, разбор и проверка (https, публичный хост, без пути/параметров, нормализация).
- `internal/api/instance.go`: поле `push_server` в `GET /api/v1/instance`, только при валидном адресе; без секретов.
- Тесты: переменная есть/нет/неверная; поле в ответе; отсутствие поля при пустом адресе; адрес не попадает в журналы как секрет (это адрес сервера, не тема).
- `go test ./internal/config ./internal/api`.

### Шаг 2. Мастерская: установка и пульт

- `Spec.PushDomain`, `Spec.PushCache`; `push.json` как источник настроек; генерация `push.yaml`, `ntfy.yml`, блока Caddy, строки `COMPOSE_FILE` в `.env`; проверка DNS и сертификата; установка, обновление, откат, удаление, осмотр; поле «Хранить сообщения» в пульте (значение — в `push.json` и `ntfy.yml`, перезапуск `push`, проверка здоровья).
- Сохранение `push.json` (домен и кэш) при обновлении и откате; удаление только своих файлов/блока; установка без шага не меняется.
- Тесты: `push.yaml` и Caddy; `.env`; установка без шага; обновление с шагом; откат; удаление; смена кэша; чужой контейнер/том/сертификат не задет.
- **Кадры до кода:** шаг установки «Сервер уведомлений», строка/состояние в пульте и поле «Хранить сообщения». Собрать из существующих компонентов Мастерской (`App.svelte`, `Button`, `Notice`), снять настоящий рендер окна, показать владельцу по одному кадру, получить «Принимаем».
- Ворота: `go test ./internal/workshop/...`, сборка окна, живой проход на пробном VPS.

### Шаг 3. Проверка контейнера ntfy

Отдельный стенд (пробный VPS или локальный Docker), протокол в `docs/testing/`:

- `/v1/health` — 200.
- Веб-корень снаружи — 404/закрыт; регистрация недоступна.
- Публикация в обычную тему — отказ; публикация в `up*` — принимается после подписки.
- Анонимная подписка на `up*` — работает; анонимное чтение обычной темы — отказ.
- Тело `aes128gcm` от `internal/push` принимается и доходит до доставщика (проверка на телефоне с обычным ntfy).
- До подписки — 507; после пропажи подписчика — 410 по правилам ntfy; поведение записать.
- В журналах нет адресов подписок и тем (SEC-7).
- Смена `cache-duration` из пульта: `ntfy.yml` обновился, сервис перезапустился, здоровье 200; старое значение не осталось.
- Зафиксировать версию образа и точные ключи `ntfy.yml`.

### Шаг 4. Живая приёмка сервера

На пробном VPS, не на боевых wynd2/wynd3:

- Установка Wynd с шагом «Сервер уведомлений»; DNS `push.<домен>` указывает заранее; сертификат выдан; `/v1/health` 200.
- `GET /api/v1/instance` отдаёт `push_server`.
- На телефоне — обычное приложение ntfy, вручную настроенное на `https://push.<домен>`; включить уведомления в Wynd (старый путь), получить пуш о записи/отклике.
- Установка без шага, обновление, откат и удаление прежней установки не меняются; удаление сервера уведомлений не трогает основной сайт.
- Смена кэша в пульте: значение применилось, сервис перезапустился, пуш снова доходит.
- Проход безопасности по `SECURITY.md`; запись в `docs/testing/pending-device-checks.md`.
- Выпуск: сервер + Мастерская; протокол выпуска; CHANGELOG; `docs/OPERATOR.md` (если план 70 к тому времени принят).

## Этап 2 — доставщик

### Шаг 5. Форк и репозиторий

- Создать `wynd-push-android` от закреплённого тега `ntfy-android`; сохранить Apache-2.0, NOTICE и историю; переименовать приложение в «Wynd Push», пакет `mixeme.wynd.push`.
- Убрать запечённый `app_base_url` (ntfy.sh) для свежей установки; ручное добавление сервера оставить.
- Сборка без Firebase; CI: тесты, lint, сборка; подпись — отдельный ключ в «Подписи»; GitHub Releases; карточка Google Play (политика конфиденциальности, data safety, скриншоты — по протоколу основного Wynd); F-Droid — позже вместе с Wynd.
- **Самообновление — сразу:** в `standard`-сборке (GitHub) проверка versionCode, подписи APK и хеша ассета, скачивание и установка через FileProvider; без 72-часовой выдержки, как у Wynd до 1.0.0. Play-сборка без самообновления. Реализация своя, код обновления Wynd (AGPL) не копируется — форк остаётся Apache-2.0. Тесты: старая версия видит новую, подпись/хеш не совпали — отказ, установка не начинается.
- **Кадры:** строка «Вышла версия …» и экран обновления — настоящий рендер приложения, показать владельцу, получить «Принимаем».

### Шаг 6. Список адресов и защищённый контракт

- Activity подтверждения (exported) + чтение списка через bound service/ContentProvider без права записи; операции `list`, `ensure(address)`, `activate(address)`; изменение — только после нажатия в доставщике. Проверка адреса; тесты (unit + instrumentation): чужое приложение может открыть диалог, но не меняет настройку без подтверждения; наш Wynd получает список и переключает после подтверждения.
- Настройки доставщика: список адресов, активный, добавление/удаление, предупреждение о смене для всех UP-подписок.
- **Кадры:** список адресов и вопрос о переключении — настоящий рендер приложения, показать владельцу, получить «Принимаем».

### Шаг 7. Wynd на Android

- `PushBridge`/`web/src/lib/android/push.ts`: передача `push_server` в доставщик; статус «адрес известен/новый/активен»; вызов активации после согласия.
- Экран «Настройки → Приложение»: умный выбор доставщика, кнопка установки Wynd Push, вторичная ссылка на список UP-доставщиков, подсказка при отсутствии `push_server`. Существующие подписки не трогаются.
- **Кадры:** изменённый экран настроек — настоящий рендер, показать владельцу, получить «Принимаем»; сверить с утверждённым экраном при том же размере/теме.
- Тесты: новый пользователь без доставщика; с Wynd Push; с другим доставщиком; с существующей подпиской; без адреса; отказ в переключении.

### Шаг 8. Живая приёмка доставщика

- Телефон (OPPO/realme): установить Wynd Push; новый пользователь; включить уведомления; адрес добавлен; вопрос о переключении; пуш приходит; запись в реестр.
- Другое UP-приложение через Wynd Push — получает свои уведомления.
- Переключение на второй адрес; предупреждение; подписки перерегистрируются; Wynd продолжает получать.
- Существующая рабочая подписка (внешний ntfy) не меняется и не анонсируется.
- Нет `push_server` — подсказка, без молчаливого ntfy.sh.
- Удаление/отключение доставщика; поведение Wynd.
- Самообновление: установить предыдущую версию, выпустить новую с другим versionCode, получить строку «Вышла версия …», обновиться; подделанный хеш/подпись — отказ.
- Выпуск Wynd Push 0.1.0 и обновление Android Wynd; протокол; CHANGELOG; карточки GitHub/Play.

## Безопасность

- **Сервер:** закрытый режим; только `up*` анонимно rw; публичной регистрации и веб-интерфейса нет; вложения и метрики выключены; кэш — значение админа (по умолчанию 12 ч); лимиты ntfy; TLS Caddy; HSTS; только свой контейнер.
- **Содержимое:** сигналы уже шифруются `aes128gcm`; сервер видит тему, время и размер, но не текст. Тема — секрет; адреса тем не логировать и не писать в документы (SEC-7).
- **Доставщик:** изменение адреса — только после подтверждения в интерфейсе доставщика; exported-компонент не меняет настройку сам; адрес проверяется; чужое приложение не может перенастроить молча; веб-страница не вызывает компонент напрямую.
- **Злоупотребления:** `visitor-subscriber-rate-limiting`, лимиты запросов и размера; публикация в неизвестную тему не создаёт её; при необходимости — ограничение по IP на Caddy.
- **Мастерская:** ставит и удаляет только свой сервис; чужие контейнеры, тома и сертификаты не трогает; DNS остаётся за владельцем.
- **До выпуска:** проход по `SECURITY.md`; проверить, что адрес и темы не попадают в журналы; отдельный протокол.

## Приёмка

**Этап 1 (сервер):** на пробном VPS установка с шагом, `/api/v1/instance` отдаёт адрес, обычный ntfy на телефоне получает пуш через наш сервер; смена кэша в пульте применяется; установка без шага, обновление, откат и удаление не меняются; безопасность пройдена; кадры Мастерской приняты.

**Этап 2 (доставщик):** новый пользователь на телефоне проходит путь «включил уведомления → Wynd Push → адрес → пуш пришёл»; другой UP-доставщик и чужое UP-приложение работают; существующая подписка не тронута; самообновление с предыдущей версии работает, подделка отклоняется; кадры настроек, доставщика и обновления приняты; выпуски GitHub/Play собраны и подписаны.

Смысл и вёрстка принимаются отдельно: «Принимаем» по кадрам не означает приёмку сценария, и наоборот. Проверки — в `docs/testing/pending-device-checks.md`.

## Вектор после первого выпуска (27.11)

Первый выпуск 0.1 не меняется: upstream ntfy + форк `ntfy-android`. Ниже —
решения о том, что делать после, чтобы обычному пользователю не нужно было
ставить второе приложение. Для 0.1 действует прежнее правило 11 (нет
доставщика — установка Wynd Push); после встроенного канала правило меняется на
описанное здесь.

### Выбор канала на телефоне

- **Есть UP-доставщик** (любой: Wynd Push, ntfy, Sunup) — используем его.
  Встроенный клиент не запускается, второй доставщик не ставим, существующие
  подписки не трогаем.
- **Доставщика нет** — встроенный клиент Wynd. Это канал журнала Wynd-сервера,
  **не** встроенный ntfy-клиент: ntfy и шаг Мастерской ему не нужны.
  Пользователь выбирает режим:
  - **pull** — WorkManager, 15+ минут (в Doze дольше), без постоянного
    уведомления, экономит батарею;
  - **FGS** — SSE, мгновенно, постоянное уведомление, больше батареи; тип FGS
    для Google Play проверить до реализации (`remoteMessaging`/`specialUse`).
- **Доставщика нет, но пользователь ставит другие UP-приложения** — предлагаем
  Wynd Push как общий доставщик; после согласия переключаем Wynd на него и
  выключаем встроенный канал.
- **Доставщик удалён или сломан** — возвращаемся на встроенный канал, с
  вопросом пользователю.
- **Один канал на пару «сервер + учётная запись»** — встроенный и UP
  одновременно не работают, дублей нет.
- **Wynd Push — предложение, не обязанность.** Если у пользователя уже есть
  рабочий доставщик, второй не нужен; Wynd Push предлагаем, когда доставщика
  нет и нужен общий на несколько приложений, или когда пользователь хочет
  именно наш.

### Сервер (предложение по реализации)

- Встроенный канал: журнал сигналов в Wynd-сервере (`notify_signals`: id,
  account_id, payload, created_at; TTL 24 ч), `GET /api/v1/notify/pending?since=`
  и для FGS `GET /api/v1/notify/stream?since=` (SSE). Сигнал — тот же
  `push.Signal`, что у Web Push; настройки уведомлений проверяются на сервере;
  клиент хранит курсор; на первой установке курсор ставится на текущий
  максимум, без пачки старых уведомлений.
- UP-путь не меняется: `POST /api/v1/push/subscribe` + Web Push на endpoint;
  ntfy-сервер (шаг Мастерской или внешний) остаётся UP-совместимым
  push-сервером.
- Шаг Мастерской «Сервер уведомлений» после появления встроенного канала нужен
  только для UP и сообщества; установка без UP-пользователей может его не
  включать.
- Встроенный канал не требует `push_server`, поддомена и сертификата; UP-путь
  требует.
- Свой Web Push-сервер внутри Wynd не делаем: встроенный канал закрывает Wynd,
  ntfy закрывает UP. Вернуться — только если контейнер/поддомен станет реальной
  проблемой.

### Мультисерверность

Обязательно решаем позже, сейчас не приоритет. Встроенный клиент естественно
обслуживает несколько входов и серверов (отдельное соединение/курсор на
каждый). У UP-доставщика один активный адрес; несколько Wynd-серверов с
разными push-серверами — ограничение форка, уже отложенное в плане.

### Открыто

- Режим по умолчанию для встроенного клиента: pull («экономно») или FGS
  («мгновенно»). Предложение — pull, FGS — осознанный выбор.
- Тип FGS для Google Play; если `remoteMessaging` не подходит, мгновенный
  встроенный режим остаётся для F-Droid, а Play-сборка — pull/UP.
- Живые проверки: OPPO/realme, экран выключен, перезагрузка, смена сети,
  24 часа, батарея, Doze, убийство процесса.
- FCM — только документальный последний резерв, вне вектора.
