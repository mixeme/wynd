# 45 — Настольное приложение для установки Wynd на удалённый сервер

**Тип:** новая возможность (развёртывание)
**Статус:** макет утверждён 2026-10-03 (`docs/visual/installer.html`); срезы 1 и 2 сделаны (подключение, отпечаток, осмотр — 2026-10-08; план и установка на чистый сервер — 2026-10-09)
**Дата:** 2026-09-27
**Срез:** `main` @ `276be18`, версия 0.10.0.

Человек без опыта администрирования ставит Wynd на свой VPS из настольного приложения: вводит адрес сервера и доступ, приложение само подключается по SSH, ставит Wynd и отдаёт ссылку первого запуска.

---

## Для кого

Для новичка, который впервые держит сервер. Администратор ставит через `install.sh` или Docker — под него приложение не подстраивается. Отсюда:

- ни одного вопроса, на который новичок не знает ответа: всё, что можно узнать осмотром, узнаётся осмотром; выбор — только там, где без человека нельзя, и с вариантом по умолчанию;
- слова человека, а не админа: «адрес сервера», «пароль от сервера», а не «хост», «vhost», «ACME»; термины — только в подробностях шага;
- объяснять, что делать, а не что сломалось: «Домен ещё не указывает на этот сервер — проверьте запись у регистратора, это может занять до часа»;
- чужое на сервере не трогать и не предлагать «починить» — только сказать, что найдено и почему это мешает.

## Почему

Сейчас установка — это `deploy/install.sh` или Docker (`deploy/docker/`) плюс прокси и сертификат (`deploy/proxy/`, `deploy/caddy/`). Всё это делается руками в терминале на сервере. Развёртывание на wynd.mixfed.ru (0.9.x) показало, сколько там шагов: SSH-ключ и known_hosts, Docker, compose, vhost прокси, certbot, синхронизация часов, доверенные прокси, проверка `/admin/check`. Владельцу круга это не по силам — а свой сервер и есть главная идея Wynd.

## Срезы

Делается срезами, каждый проверяется на настоящем сервере.

- [x] **1. Подключение, отпечаток, осмотр** (окна 1, 1а, 2, 2а) — 2026-10-08. На сервере ничего не меняется.
  - `internal/installer`: `Dialer` (SSH в процессе, `known_hosts` из `~/.ssh`), `Inspect` (одна команда только на чтение, разбор в находки `ok` / `note` / `block` словами человека), `CheckDomain`, `Wizard` — сценарий окна. Покрыто тестами с подставным SSH-сервером; пакет идёт в общих воротах.
  - `cmd/wynd-installer`: оболочка Wails v2 и окно на Svelte из `$ui` (`frontend/`, псевдонимы `$ui` и `$lib` ведут в `web/src/lib`). Пакет собирается только с метками Wails (`dev`, `desktop`, `bindings`) — `go vet ./...` и `go test ./...` сервера его не видят.
  - Осмотр: система (Debian и Ubuntu, x86-64 и ARM64), права, свободное место (помеха — только если не поместится сама установка: меньше 2 ГБ, с Docker — 1 ГБ), часы (расхождение больше минуты или нет синхронизации — «настроим»), Docker и Compose, кто держит порты 80 и 443 (nginx, Apache, Caddy — «встанем за ним»; иное — помеха), уже стоящий Wynd, адреса сервера. Домен сверяется с адресом подключения и адресами сервера.
  - Пароль: по умолчанию живёт в памяти, пока окно открыто; с галочкой «Запомнить пароль» кладётся в связку ключей системы после удачного входа, без галочки — стирается оттуда (решение 2026-10-08, вместо «всегда в связке» из макета).
  - Чего в срезе нет: «Создать ключ», ключи под паролем и ssh-agent (берутся незащищённые `id_ed25519`, `id_ecdsa`, `id_rsa`), порт SSH кроме 22, кнопка «Дальше — план» погашена. Фронтенд лежит в `cmd/wynd-installer/frontend`, а не рядом с `web/`: `go:embed` не выходит за каталог пакета.
  - Проверено на этой машине: окно в `wails dev` против подставного сервера (отпечаток, неверный пароль, осмотр, помеха, проверка домена, запоминание пароля в Диспетчере учётных данных), сборка `wails build` (13 МБ). На настоящем сервере не проверено — ждёт данных тестового сервера.
- [x] **2. План и установка на чистый сервер** (окна 3, 4, 4а, 5) — 2026-10-09.
  - `internal/installer/install.go`: `BuildPlan` (поставим / изменим / не тронем по осмотру), `Install` — шаги *уже сделано? / сделать / убедиться*, `Rollback`. Шаги: Docker (из репозитория Docker, как велит его документация), синхронизация часов (только если осмотр её просил), образ Wynd, файлы `/opt/wynd/compose.yaml` и `Caddyfile`, запуск, сертификат, проверка со ссылкой первого запуска. Повторный запуск на готовом сервере меняет только `docker compose up -d` (тест).
  - Отказ шага — словами и с советом (`Failure`): замок пакетов, нет интернета, кончилось место, заняты порты, сертификат не выдали, шаг идёт дольше срока (`ErrTimeout` — не путать с оборванной связью). Команды и вывод — в журнале для «показать, что выполняется»; ссылка первого запуска в журнал не попадает.
  - Файлы — те же, что в `deploy/docker/compose.yaml` и `deploy/caddy/Caddyfile`, только готовый образ вместо сборки и без почты для Let's Encrypt; тест сверяет их с `deploy/` и упадёт, если разойдутся.
  - Образ: `ImageSource`. Основной способ — `RegistryImage`: сервер сам скачивает `ghcr.io/mixeme/wynd:<версия>` (решение владельца, 2026-10-09: реестр — GitHub); в `compose.yaml` стоит полное имя, администратор обновляет обычным `docker compose pull`. Образ публикует `.github/workflows/image.yaml` при смене `VERSION`, под x86-64 и ARM64. Запасной способ — `TarImage`: файл `docker save` с этого компьютера уезжает по тому же SSH в `docker load`; в `wails dev` его задаёт `WYND_INSTALLER_IMAGE`. Версии нет в реестре — «Этой версии Wynd в хранилище ещё нет». **Из реестра на живом сервере не ставили:** зеркала на GitHub ещё нет.
  - Ссылка первого запуска — настоящая: `bootstrap URL` из журнала контейнера (`/admin/bootstrap?token=…`), срока у неё нет. Макет (окно 5) исправлен: было `/setup/…` и «действует сутки».
  - Сертификат проверяется с компьютера человека (сайт открывается снаружи, сертификат действует); если у компьютера не работает DNS — с сервера, это слабее.
  - Откат: `docker compose down`, папка `/opt/wynd`, образ Wynd; данные (тома) — только по галочке «Удалить и данные Wynd». Docker остаётся.
  - Окно: «Дальше — план» → план → «Установить» → шаги живьём (окно спрашивает ход раз в полсекунды) → «Wynd работает» со ссылкой; отказ — «Повторить» / «Откатить установку» / «подробности».
  - Чего в срезе нет: сервер с чужим веб-сервером (план отвечает «в следующей версии»), смена адреса у стоящего Wynd (отказ с советом), адрес не латиницей, пользователь не root проверен только кодом (`sudo -n sh -c`), образ из реестра.
- [ ] **3. Сервер с чужим прокси**: шаблон под nginx, Apache, Caddy с резервной копией и откатом.
- [ ] **4. Пульт** (окно 6): обновление с бэкапом, откат, бэкап на компьютер, несколько серверов.
- [ ] **До выпуска:** зеркало на GitHub и первый прогон `.github/workflows/image.yaml`; пакет `wynd` в ghcr.io открыть (Package settings → Change visibility → Public), иначе сервер не скачает образ без входа; установка из реестра на живом сервере; аудит безопасности; лицензии зависимостей самого установщика (сейчас `THIRD_PARTY_LICENSES.txt` собирается только для `cmd/wynd`); сборка под Linux; подпись.

## С чего продолжить

Состояние на 2026-10-08, коммит `306e675`. Срез 1 в Gitea; на настоящем сервере не запускался.

**Ждём от владельца:** файл в `dev/` (в git не попадает) с адресом, пользователем и паролем чистого тестового сервера и домен, который на него указывает. Сервер тестовый, утечка пароля рисков не несёт (слова владельца, 2026-10-08). На wynd.mixfed.ru установку не пробовать.

**Проба на чистом VPS, 2026-10-08** (адрес и доступ — в локальном файле разработчика; домена пока нет). Ядро запускалось пробой `dev/probe` (в git не попадает), `known_hosts` — копия настоящего.
- Настоящий `known_hosts` из профиля с кириллицей читается; отпечаток дописан одной строкой после строки с CRLF, файл цел.
- Сервер отвечает медленно: приветствие SSH приходит через ~10 с, всё рукопожатие — ~15 с. Общий срок 15 с давал «Сервер не отвечает» на живом сервере. Исправлено: 15 с на TCP, отдельные 60 с на рукопожатие и вход (`handshakeTimeout`).
- Вход паролем сначала не прошёл («Сервер не принял пароль»); после исправления пароля владельцем (2026-10-09) вход прошёл.
- Осмотр сверен с сырым выводом: Debian 12 x86-64, root, свободно 5,4 ГБ из 7, часы верны и сверяются (`systemd-timesyncd` уже работает), Docker нет, порты 80 и 443 свободны, один адрес. Все находки совпали с выводом `ss`, `df`, `ip`, `timedatectl`.
- Пробный домен (записан с точкой на конце) — «указывает на этот сервер».
- Что эта машина говорит срезу 2: 1 ядро, 708 МБ памяти, 7 ГБ диска — собирать образ на сервере нельзя, только привозить готовый; свободного места чуть выше порога в 5 ГБ, после Docker и образа его надо перепроверять; `gpg` нет (репозиторий Docker его требует), `curl` и `wget` есть; ufw, nftables и fail2ban не стоят.

**Шаг 1 — срез 1 на настоящем сервере.** Запустить `wails dev` без переменных `WYND_INSTALLER_SSH_*` (или собранный `build/bin/wynd-installer.exe`), подключиться к тестовому серверу, пройти отпечаток и осмотр. Смотреть:
- отпечаток лёг в настоящий `~/.ssh/known_hosts` одной строкой, файл не испорчен (имя профиля — кириллицей);
- вывод настоящих `ss -H -ltnp`, `df -Pk /`, `ip -4 -o addr`, `timedatectl show` разбирается: «подробнее, что проверили» показывает сырой вывод, сверить с находками; разбор писался по образцам, а не по живому серверу;
- домен: «указывает на этот сервер» при верной записи A; на машине разработки локальный DNS бывает мёртв (VPN) — тогда «Не удалось проверить адрес сайта», это не ошибка окна;
- «Запомнить пароль»: запись «Wynd Installer» в Диспетчере учётных данных Windows появляется и исчезает со снятой галочкой;
- вид окна глазами: скриншот из панели браузера в прошлой сессии не снимался, вёрстка проверена только по размерам элементов.

**Срез 2 на настоящем сервере, 2026-10-09** (пробный VPS: Debian 12, 1 ядро, 708 МБ, диск 7 ГБ; проба без окна — `dev/install-probe`, образ — `docker save` с рабочего сервера в `dev/images/`).
- Итог: Wynd 0.28.7 стоит, сайт на пробном домене открывается снаружи с действующим сертификатом, ссылка первого запуска получена. Повторный запуск на готовом сервере прошёл за три минуты и ничего не поменял.
- Сервер очень медленный (диск: ожидание ввода-вывода 100 %): Docker ставился около 25 минут, `docker load` после отправки 55 МБ — 7 минут, `docker compose up` — 16 минут. Вся установка — 27 минут чистого времени плюс три оборванные попытки. Отсюда правки: срок на пакеты и запуск — 40 минут, на ответ Wynd — 5 минут; «шаг идёт дольше, чем мы ждали» отдельно от «связь оборвалась»; apt ждёт замок пакетов 10 минут; подпись «сервер распаковывает Wynd» после отправки образа.
- Что нашлось только на живом сервере:
  - оборванная по сроку команда на сервере продолжает идти: следующая попытка упиралась в замок пакетов от нашей же прошлой — теперь ждёт его, а отказ объясняет обе причины;
  - после оборванной установки `docker` и `docker compose` уже отвечают, а служба ещё не запущена — «Docker готов» теперь спрашивает и службу (`docker info`);
  - порог свободного места 5 ГБ запрещал продолжить установку на диске 7 ГБ (после пакетов Docker осталось 4,8 ГБ). Решение владельца, 2026-10-09: порог под будущие записи бессмыслен — кто сколько выложит медиа, неизвестно, а для текста хватит любого диска. Осмотр проверяет только, поместится ли сама установка: 2 ГБ, с Docker 1 ГБ (Docker занял 0,7 ГБ, образы — 0,4 ГБ);
  - повторный осмотр принимал собственный Caddy за чужую программу на портах 80 и 443 — теперь узнаёт контейнер из `/opt/wynd`.
- Окно против этого же сервера (`wails dev`, в браузере на `localhost:34115`; пароль в окно не вводился — подставлен переменной `WYND_INSTALLER_PASSWORD`, только в сборке разработчика): подключение, осмотр, проверка адреса, план, шаги установки живьём, экран отказа с «подробностями» — отработали. Экран «Wynd работает» в окне не увиден: к тому времени сервер перестал отвечать в срок.
- Окно показало ложный отказ «Сертификат не выдали»: сайт работал, но с машины разработки отвечал через 17–25 секунд и через раз (прокси). Теперь сайт, не открывшийся с компьютера, проверяется с самого сервера: сертификат Let's Encrypt выдаёт, только зайдя снаружи, так что действующий сертификат и есть доказательство открытых портов.
- После установки сервер стал отвечать совсем медленно: вход по SSH — 75 секунд, потом две с половиной минуты; сайт — 25 секунд. Сначала я списал это на память (708 МБ) и добавил в осмотр предупреждение «памяти мало» — **ошибочно**: замер на сервере показал 430 МБ свободной памяти и давление ввода-вывода 86 % при почти нулевом обмене с диском (`/proc/pressure/io`, `vmstat`). Болен диск этого VPS (или хостер его душит), а не наша установка. Предупреждение о памяти убрано; срок рукопожатия SSH оставлен в две минуты.
- Откат на живом сервере (с сохранением данных) прошёл: контейнеры и сеть убраны, `/opt/wynd` нет, образ Wynd удалён, три тома с данными на месте. Образ Caddy оставался — теперь откат убирает и его.
- Не проверено на живом сервере: откат с удалением данных, установка заново поверх сохранённых данных, отказ сертификата при закрытых портах, синхронизация часов (на этом сервере она уже работала), экран «Wynd работает» в окне. **Дальше этот VPS непригоден для проб**, пока диск не оживёт: нужна переустановка системы или другой сервер.

Решения владельца не получены, приняты мои предложения (2026-10-09): образ привозим готовым по SSH; ссылка первого запуска — из журнала контейнера; `systemd-timesyncd` — «поставим», без резервной копии; откат убирает только своё, данные — по галочке; чистый сервер получает свой Caddy, как в `deploy/docker`. Про пробный VPS владелец сказал: «систему на машине можно поставить другую, если надо» — ставлю на него без отдельного вопроса.

**Дальше — срез 3** (сервер с чужим nginx, Apache или Caddy): шаблоны `deploy/proxy/*` и `compose.own-proxy.yaml`, резервная копия изменённого файла, откат возвращает её. Чужих серверов для пробы нет (владелец, 2026-10-09: «придётся имитировать их самим») — на пробный VPS ставим nginx, Apache или Caddy с сайтом-заглушкой сами и ставим Wynd рядом. Систему на VPS после переустановки взять Ubuntu 24.04: Debian 12 уже пройден, а Ubuntu — вторая из двух поддержанных и самая частая у хостеров.

**Как проверять без сервера.** `dev/fakessh/main.go` — подставной SSH на `127.0.0.1:2222`, пароль `test`, на любую команду отдаёт файл из первого аргумента. Запуск окна против него: `WYND_INSTALLER_SSH_PORT=2222 WYND_INSTALLER_SSH_DIR=<пустой каталог> wails dev -browser=false`, затем `http://localhost:34115` в браузере — привязки Go там работают. Правки в `internal/installer` `wails dev` не подхватывает — перезапустить. После остановки `wails dev` остаётся процесс Vite на порту 5175 — снять вручную.

**Долги среза 2:** экран «Wynd работает» и откат в окне против настоящего сервера; пользователь не root; подставной сервер для окна (`dev/fakessh`) отвечает одним выводом на всё и установку не изображает; проверка сертификата «снаружи» идёт с компьютера человека и слепа, если у того мёртвый DNS.

**Долги среза 1:** «Создать ключ», ключи под паролем, ssh-agent, порт SSH кроме 22; проверка окна (`npm run check` во `frontend/`) не входит в `scripts\test.bat`; у окна нет тестов — только ядро.

## Решения

- **Стек — Go + Wails**, в этом репозитории (`cmd/wynd-installer`, фронтенд рядом с `web/`). Бэкенд переиспользует `internal/check` и шаблоны прокси из `internal/api/admin_check.go`, окно — Svelte и `$ui`, как у клиента. Wails, а не Tauri: Tauri добавил бы Rust ради того, что Go уже умеет. Fyne отпадает: свой набор виджетов не даёт взять `$ui`. Версию Wails выбрать при старте: v2 стабильна, v3 — только если к тому времени вышел релиз.
- **Секреты — в системной связке ключей** (Credential Manager, Keychain, Secret Service), не в файлах приложения.
- **SSH — системные ключи и доверие**: `~/.ssh` (ключи, `known_hosts`, `config`) и системный ssh-agent (на Windows — канал агента OpenSSH). Протокол — `golang.org/x/crypto/ssh` и `knownhosts` в процессе, без запуска `ssh.exe`: сборки ssh на Windows (Git, OpenSSH) по-разному читают пути с кириллицей в профиле — это видно на машине разработки.
- **Автообновление приложения — позже**, не в первом выпуске. Подпись сборок — вопрос первого публичного выпуска.
- **Аудит безопасности обязателен** до выпуска: секреты в новом месте, исходящие SSH-подключения, команды на чужом сервере (SECURITY.md, «Когда нужен повторный проход»).

- **ОС сервера — Debian и Ubuntu.** Другие — отказ с понятной причиной после осмотра, до любых изменений.
- **ОС приложения — Windows и Linux.** Код один, но собирать на каждой ОС отдельно: Wails на Linux требует cgo и WebKitGTK, из Windows его не собрать. На Windows 10 нужен WebView2, он ставится вместе с приложением (в Windows 11 уже есть).
- **Установщик — не обёртка над `install.sh`, а сценарий шагов на Go.** У каждого шага три части: *проверить* (уже сделано? что мешает?), *сделать*, *убедиться*. Отсюда:
  - повторный запуск безопасен — сделанное пропускается, оборванное доделывается;
  - перед изменениями человек видит план: что будет поставлено, что изменено, что найдено чужого и не будет тронуто;
  - ошибка шага объясняется словами и с советом, а не выводом команды;
  - занятый порт, свой прокси, отсутствие DNS-записи, неверные часы, мало места — ловятся на осмотре, до установки;
  - меняемые файлы (vhost прокси, compose) — сначала резервная копия, откат шага возвращает её.

- **`deploy/install.sh` остаётся** — для того, кто сам администрирует сервер и не станет ставить отдельную программу ради очередного сервиса. Оба пути поддерживаются: приложение не заменяет скрипт и Docker-шаблоны, а ведёт по ним того, кто сам не справится. Результат должен быть одинаковым — установку из приложения администратор потом обслуживает руками по той же документации.
