# Действующая поза безопасности

Состояние защиты на 2026-11-22. Состав маршрутов сверен с кодом (`internal/api/server.go`: 174 регистрации, раскладка та же, что в отчёте 04.11), механики — с кодом и журналами ниже. Проход аудита обновляет этот раздел тем же коммитом. Подробности механик — [server-reference](reference/server-reference.md), client-reference, desktop-reference.

## Шлюзы и состав маршрутов

Обёртки (`internal/api/server.go`, `respond.go`, `admin.go`):

| Шлюз | Что проверяет |
|---|---|
| без обёртки / `public` (= `limitBody`) | только лимит тела 1 МиБ; авторизации нет |
| `limitProbe` | 12 запросов/мин/IP; тело ≤ `body_probe_bytes` |
| `admin` | Bearer, `kind=admin`, 8 ч |
| `participant` / `RequireParticipantStream` | Bearer, `kind=participant`, 30 дней; `blocked`/`deleted_at` проверяются при каждом запросе |
| `paid` | participant + оплата: `required && expired && has_requisites` → 403 `payment_required` |
| `withReviveBody` | participant + оплата + свой лимит тела |
| bearer-ссылки | `/move*` — ключ переноса; `/archive/{token}`, `/full_archive*` — токен ссылки |

Токен — только заголовок `Authorization`; cookie и `?token=` нет; CORS в сервере нет; `nosniff` на каждом ответе.

Состав (174): **без сессии 20** — `/instance`, четыре `/probe*`, `auth/register|code|verify`, приглашение (просмотр/принятие), `admin/bootstrap`(+`smtp-test`), `admin/login`, четыре `/move*` (ключ переноса), три ссылки архивов (токен); **admin 47** — панель: инвайты сервера, хранилище и квоты, сжатие, доступ/пароль/почта, учётки, SMTP и проба, VAPID и тест-пуш, `admin/check`, прокси-сниппеты, заявки на квоту, оплата (реквизиты, донат, подписка, заявки, блобы заявок, учётки); **participant 14** — вход/выход, смена почты, уход, загрузки ×4 (вне `paid` осознанно: истёкшему нужен скриншот оплаты, аудит 22.09), `appearance` ×2, `pay` ×3; **paid 92** — круги и членство (лента, дни, сетка, карта, поиск, участники, лица, приглашения и заявки, группы, отклики), контент (записи, комментарии, реакции, заголовки и обложки дней), `notify_prefs`, push-подписка, блобы, полный архив и оживление, перенос, архивный цикл; **withReviveBody 1** — `POST /revive`.

Предметные права внутри paid — `internal/chronicle/gate.go`: `requireReader` (не `gone`, есть `can_read`-отрезок) → `requireWriter` (`active` + открытый `can_write`-отрезок) → `requireAuthor` (своя identity); `requireSettingsTx`, `RequireCanInvite`, `RequireOwner` — в транзакции. Доступ к блобу — `CanAccessBlob`: владелец / `post_media` в отрезке читателя / аватар лица круга.

## Лимиты и тела

JSON — `MaxBytesReader` 1 МиБ (413 `payload_too_large`). Тексты: пост 20 000, комментарий 2 000, имя 100, заголовок дня 200; заявка оплаты/реквизиты/баннер — 2 000/4 000/4 000; `days` ≤ 3660. Коды входа: 10/IP/час + 5/почту/час, TTL 15 мин, 3 попытки атомарно (`UPDATE … WHERE attempts < 3`), сравнение хеша константное. `/auth/verify` — 10 неудач/15 мин/IP. `admin/login` — 5/15 мин/IP, глобальный ключ замедляет на 2 с вместо запрета. `client_id` ≤ 64, `MaxPostMedia` = 50; инвайты: `max_uses` ≤ 1000, `ttl` ≤ 365 д, отложенное вступление — 24 ч и снимается отзывом ссылки/исключением пригласившего. Открытая регистрация отвечает «код отправлен» без письма и заблокированному — иначе endpoint был бы справочником учёток. Входящий перенос: чанк ≤ 32 МиБ, общий бюджет и резерв диска с проверкой свободного места, лимит одновременных операций, потолки распакованных таблиц (SEC-03, 04.11).

## Секреты

`wynd.db` 0600 (выравнивается при старте), `keys/*` 0600, `config.json` 0640 без секретов, каталог бэкапа 0700, копия базы — `VACUUM INTO` 0600. В БД открытым текстом SMTP-пароль и приватный VAPID (риск DEC-1); токены сессий — `sha256(token)`, пароль админа — bcrypt ≥ 8, коды — SHA-256. В логах токенов и кодов нет (коды — только loopback-фолбэк, файл 0600; bootstrap-URL с токеном до установки — и есть канал доставки). `wynd admin-password` и `wynd backup` — запускать от пользователя службы.

## Исходящие запросы сервера

SMTP — адрес админа, 15 с, TLS 465 или обязательный STARTTLS вне loopback, сертификат проверяется. Push — endpoint участника: `dialPublicOnly` проверяет каждый IP каждого соединения (loopback/private/link-local/CGNAT отвергаются), редиректы запрещены, таймауты 5/10 с, при подписке — только `https` и публичный IP. `admin/check` — только `public_url` админа: DNS, TLS-проба, HTTP-редирект без чтения тела, NTP `pool.ntp.org`, исходящий адрес — UDP-сокет без отправки. Входящий перенос — публичные адреса на каждом соединении, соединение с проверенным IP, редиректы запрещены; LAN-исключение — только явные `MoveAllowedNetworks` оператора. `InsecureSkipVerify` в сервере нет (единственное место экосистемы — Мастерская: показать сертификат на подтверждение отпечатка).

## Отдача файлов

Блобы — `attachment` + `nosniff`, опасные MIME (svg/html/js/xml-семейство) → `octet-stream`, имя файла — UUID, путь на диске из БД, не из URL. Архивы — потоком, не целиком в памяти; одна сборка на учётку (429 + `Retry-After`). Полный архив — снимок в БД и виртуальный ZIP: Range/ETag/If-Range, размер и SHA-256 проверяются до публикации, снимок удерживает файлы от GC, не давая нового доступа через blob API. Ссылки участника — одноразовые, минутные (`LoadAndDelete`); повторная браузерная навигация — публичное пояснение без личных данных.

## Клиент

`{@html}` — только манифест PWA и SVG QR-кода; `src` — только `blob:`; автолинковки нет. Токены — в IndexedDB, а в приложении Android (C127) — в общем файле оболочки (`secrets.json`, app-private, каталог данных приложения); `Authorization` — строго на origin своего сервера. Любое поле сервера, попадающее в `href`, — только `http:`/`https:` (правило `source_url`, 27.09). Приглашение из вставки или QR — только свой origin, токен чужому серверу не уходит. Открытого редиректа после входа нет.

## Оболочки

**Настольный** — тонкая оболочка вокруг выбранного сервера: страница в `iframe` того же origin (`wails.localhost`); мост — только в HTML выбранного сервера, данные моста — адрес сервера и `apiBase`, не секреты. Локальный порт `127.0.0.1:0` (случайный) проксирует выбранный сервер, CORS — только origin'ы страницы окна. Прочие серверы — через `/__srv/…` по хранилищу, а не по URL: неизвестный адрес — 403. `servers.json` 0600/0700 без токенов и паролей. Проверка адреса — только http/https, без логина, пути, параметров и якоря. Самообновление — только Ed25519-подписанные выпуски общим ключом экосистемы (ключ вшит при сборке), не раньше 72 ч после публикации; автозапуск — `HKCU\…\Run`, только свой exe. Подробная таблица границ — [журнал 17.11](#audit-2026-11-17).
**Мастерская** — `servers.json` без паролей и журналов (имя, SSH-адрес, пользователь, способ входа, датированный результат осмотра); пароли — в системной связке или памяти операции; запись temp+rename, чтение ≤ 4 МиБ; SSH — ограниченный временный ключ, смена отпечатка хоста — отдельное подтверждение; установка и доверие — только явные действия. Подробно — [журнал 05.11](#audit-2026-11-05).
**Подпись** — закрытый ключ у владельца; до подписи сверяются сумма exe и удостоверение GitHub Actions выбранного тега; открытый ключ из тега обязателен для проверки; пароль и закрытый ключ в CI не попадают.
**Android** — входы участника хранит оболочка в `secrets.json` в каталоге данных приложения (C127): мост `__wyndSecrets` привязан к origin выбранного интерфейса и только главному кадру, поля записи проверяются и ограничены, файл пишется атомарно. Следствие варианта «общие входы»: страница выбранного сервера (её JS присылает сервер) может прочитать токены других входов — как в окне для компьютера через `/__secrets`; вшитый клиент из APK это снимет (план 50). Подписки UnifiedPush — по паре «сервер + учётная запись», VAPID каждого сервера свой (C126).

## Развёртывание

Docker и systemd — от непривилегированного пользователя; юнит с `ProtectSystem=strict`, `ProtectProc`, `ProtectKernel*`, `ProtectClock`, `ProtectHostname`, `PrivateDevices`, `NoNewPrivileges`. `compose.own-proxy.yaml` публикует Wynd только на `127.0.0.1:7676`; шаблон Apache снимает клиентский `X-Forwarded-For`, ставит HSTS и `LimitRequestBody`. Прокси на другом хосте — прописать в `WYND_TRUSTED_PROXIES`, иначе лимиты считаются по адресу прокси. Оператору — [SECURITY.md](SECURITY.md), «Что должен сделать оператор».

## Принятые риски (суммарно)

Рассуждения и датировки — журнал по ссылкам; два главных — также в [SECURITY.md](SECURITY.md) и server-reference.

1. **Секреты в БД открытым текстом** (DEC-1; [03.09](#audit-2026-09-03), [22.09](#audit-2026-09-22)).
2. **Снимок отдаёт текущее состояние** — правки после ухода участника видны в ленте и днях, `sync` их не отдаёт ([22.09](#audit-2026-09-22)).
3. **404 на `/auth/code` в режимах invite/closed** — подсказка полезна, список участников известен приглашающему ([03.09](#audit-2026-09-03)).
4. **Advisories dev-зависимостей npm** — в рантайм статической SPA не попадают; обновление согласованными группами, не вслепую ([03.09](#audit-2026-09-03); SEC-05, [04.11](#audit-2026-11-04)).
5. **Плитки OSM** — третья сторона видит IP и район просматриваемых фото ([22.09](#audit-2026-09-22)).
6. **`http://` удалённого сервера без предупреждения** — нужен для loopback-разработки ([22.09](#audit-2026-09-22)).
7. **CSP без `script-src`** ([22.09](#audit-2026-09-22)).
8. **Оракул цикла архива** на `GET …/archive/download` до проверки членства (404/403) — UUID v7 не угадывается ([27.09](#audit-2026-09-27)).
9. **`validateEndpoint` пропускает подписку при недоступном DNS** — доставка всё равно пойдёт через `dialPublicOnly` ([27.09](#audit-2026-09-27)).
10. **NAT64-префикс к приватному IPv4** не ловится `isPublicIP` — на сервере без NAT64 недостижимо ([27.09](#audit-2026-09-27)).
11. **Режим `lan`** — без TLS, на совести запускающего; сервер предупреждает при старте ([27.09](#audit-2026-09-27)).
12. **Ключ переноса (Move bearer) даёт физический журнал** держателю токена и оператору принимающего сервера — транспорт переноса, не криптозащита от них (A19, [03.11](#audit-2026-11-03)).
13. **Полученные копии не отзываются** — начатые разрешённые ответы и выданные архивы (A19, [03.11](#audit-2026-11-03)).
14. **Порча файлов оператором или диском** не восстанавливается из индекса — получатель отвергает повреждённый круг (A21/A22, [03.11](#audit-2026-11-03)).
15. **Настольный:** выбранный сервер — доверенный код (через мост — смена источника, автозапуск, самообновление; всё подписанное/своё); локальные процессы того же пользователя видят порт и `/__srv` без токена; общая банка cookies проксированных серверов (сейчас не влияет — cookie нет; пересмотреть при cookie-аутентификации); один ключ подписи на Мастерскую и окно ([17.11](#audit-2026-11-17)).

## Открытые остатки

- Нет `ReadTimeout` на чанк загрузки — медленный клиент держит соединение; за прокси с `read_timeout` недостижимо ([27.09](#audit-2026-09-27), принято).
- Упоминание обходит mute (`notify_prefs.mentions` всегда true) — продуктовая задача, не безопасность ([27.09](#audit-2026-09-27)).
- Строка `blobs.pending` при сбое между `Rename` и коммитом — заметка плана хранения ([27.09](#audit-2026-09-27)).
- SEC-01–05 ([04.11](#audit-2026-11-04)) закрыты в 0.48.2 — [приёмка доработок](review-followup-2026-11-04.md); оставшиеся ручные проверки окна и устройств — [реестр](testing/pending-device-checks.md).

# Аудит безопасности — 2026-09-03

Срез аудита — **0.1.13→0.1.14**. Актуальная версия продукта — файл [`VERSION`](../VERSION) в корне; этот документ не переписывается под каждый релиз.

Ручной обзор всего репозитория на версии 0.1.13: Go-сервер (`internal/…`,
`cmd/wynd`), SvelteKit-клиент (`web/`), деплой-конфиги (`deploy/`) и
зависимости (`govulncheck`, `npm audit`). Все найденные пункты исправлены в
версии 0.1.14, кроме двух осознанно принятых рисков в конце.

## Что было в порядке

Проверенное без замечаний (токены из `crypto/rand`, bcrypt, параметризованный SQL, отдача вложений только `attachment`/`nosniff`, непривилегированный деплой, чистые `govulncheck`/`npm audit --omit=dev`) вошло в «Действующую позу»; дословный перечень прохода — в истории git.

## Найдено и исправлено

- **C60: неполная копия при новой загрузке.** Первый обход файлов мог закончиться до загрузки, которая уже попала в последующий снимок базы. После снимка добавлен второй инкрементальный обход. `TestBackupCapturesUploadDuringBackup` удерживает базу до новой загрузки, открывает восстановленную базу и читает файл по её пути. Проверяются полная и инкрементальная копии, сохранение удалённого источника и отсутствие перезаписи готового файла.
- **Мастерская: имя папки попадало в выражение tar.** Запятая в имени ломала команду, а специальные знаки регулярного выражения могли нарушить переименование папки в `data`. Тест `TestForeignTransferArchive` выполняет настоящую команду GNU tar для обычного имени и `data[1], old`, проверяет пути базы и фото, исключение старых копий и служебных пометок. До исправления тест падал.
- **Кавычки команды временного ключа.** Серверная команда дополнительно экранируется для поля `command="…"` в `authorized_keys`, а строка записывается через `printf`, чтобы shell не менял обратные косые черты. - Обходы файлов не блокируют работу сервера. Это не общая транзакция между SQLite и файловой системой: файл, загруженный после первого обхода и удалённый после снимка базы до второго обхода, по-прежнему может отсутствовать. Неподтверждённый хвост после остановки отбрасывается; несовпадение ETag или границ останавливает приём. Истёкшая ссылка сохраняет префикс для перевыпуска. Снимок удерживает файлы от очистки, не предоставляя нового доступа через обычный blob API.

Проверки: полный межсерверный перенос, частичный HTTP-ответ, смена представления, перезапуск обеих служб с повторным открытием баз, истечение и два перевыпуска, неизменность после правки живых данных, отсутствие исходящего файла и копии медиа в индексе, CRC ZIP и произвольные границы чтения, отказ чужому читателю, освобождение удержания и совместимость старого готового файла. API-тесты используют файловый WAL, как сервер, вместо другой модели блокировок shared-cache SQLite в памяти.

Ограничения: физическая порча файлов оператором или диском не восстанавливается из индекса; получатель проверяет ZIP и SHA-256 и не подтверждает повреждённый круг. Готовые файлы до обновления сохраняются до конца операции ради совместимости; новые переносы их не создают. Миграция 14 требует закрытого полного бэкапа и нового бинарника. Полные ворота выпуска scripts/test.bat пройдены на дереве выпуска.

## Дополнение — A22, Wynd 0.48.0

Проверены все пути появления содержимого: загрузка частями, импорт переноса, серверные кадры, оживление и отделение. Реестр физического содержимого не служит поиском для участника. Перед присоединением проверяются полученные байты либо собственная готовая копия; глобальные id и наличие чужого файла по хешу не раскрываются. Имена и MIME-типы логических копий независимы, архивные метаданные ограничиваются при восстановлении.

Проверены аккаунты с одинаковыми байтами, неверные байты при верном заявленном хеше, отдельные имена и типы, очистка первой и последней копии, параллельные публикация и GC, включая гонку последней копии, миграция существующих данных и повторный запуск после прерванной публикации. Снимки A21, аватары, обложки и оплата используют общий предикат ссылок. Удалённый скриншот лишается связи с содержимым и не возвращается через поиск собственных файлов.

Физическое удаление выполняется после коммита отделения копии, под тем же SQLite write lock, что и публикация; проверка всех оставшихся путей повторяется. Неудачные удаления остаются в очереди. Копирование бэкапа задерживает GC возобновляемой арендой между снимком базы и последним обходом файлов. Полный и инкрементальный бэкапы восстанавливают общие байты и независимые копии. Учёт инстанса физический, квоты кругов логические; правила A19 и A21 не расширяются.

Дополнительно закрыты два пути неверного повторного использования: при оживлении собственная копия сверяется по фактической сумме, а не только метаданным; старые удалённые скриншоты оплаты отделяются до объединения хешей и не восстанавливаются из другой учётки. Если скриншот ещё нужен записи, его файл держится до снятия последней ссылки, затем освобождается при сохранённой строке аудита. Оба случая покрыты регрессионными проверками.

Ограничения: порча оператором/диском не исправляется без корректной копии; отсутствующие или неверные старые файлы не удаляются миграцией. Первый запуск сверяет прежние файлы и может занять время; при невозможности жёсткой ссылки для переноса нужен временный запас диска. После аварии бэкапа GC может ждать истечения часовой аренды. Миграция 15 требует полного закрытого бэкапа и нового бинарника; новым архивам нужен получатель 0.48.0. Полные ворота выпуска scripts/test.bat пройдены на точном дереве версии до версионного коммита.

## Дополнение — C57, Wynd 0.48.1

Проверен путь архива участника: запрос ссылки с сессией, минутный одноразовый токен и скачивание браузером без заголовка входа. Эта граница доверия сохранена. Проверка занятости при выдаче ссылки идёт после проверки сессии, оплаты и чтения; чужая учётка не узнаёт состояние скачивания. Занятость не выпускает новый токен. Страница не содержит личных данных, не требует входа и не выдаёт файл. Использованные/неверные токены сохраняют прежний возврат в приложение. Redirect — no-store и no-referrer. Отказ второй загрузке не снимает блокировку первой.

Пауза не смешивается между одноимёнными кругами разных серверов. Оба варианта 6.23 и переход из баннера проверены; полный ZIP остаётся за пределами памяти клиента.

Проверки: целевые API-сценарии и семь клиентских тестов, включая истечение паузы, повтор, сетевой отказ, изоляцию серверов и публичный экран без сессии. Кадры 6.23а–б утверждены владельцем 2026-11-03.

## Открытые находки

### SEC-01 — P1 / высокая: SSRF через ссылку переноса [тест]

Где: `internal/api/move_in.go:41–94`, вызов из `handlePutIncomingMove:245`. Обычный вошедший участник, проходящий оплату, передаёт ссылку; `fetchMoveCard` обращается по ней до проверки существования настоящего переноса. Разрешены произвольные host/port, loopback и частные адреса. Запрет редиректов не закрывает прямое обращение и смену DNS между соединениями.

Дополнительно `u.Path` возвращается в URL конкатенацией. Закодированный `?` в префиксе пути превращается в начало query: локальная тестовая ссылка `/private%3F/move/AAAA-BBBB-CCCC-DDDD` привела к **GET `/private?/api/v1/move`**. Таким образом, ограничение на фиксированный API-путь тоже не удерживается. Пробник обращался только к своему `httptest`-серверу. Не утверждается чтение произвольного ответа наружу: уже подтверждены запрос к внутреннему сервису и выбор пути; код/время ответа дополнительно дают оракул доступности.

Доработка: безопасное построение URL, запрет недопустимых префиксов и непубличных адресов на каждом соединении; проверка всех DNS-результатов с соединением именно с проверенным IP, сохранение TLS hostname; редиректы остаются запрещены. Для намеренного LAN-переноса — явная конфигурация администратора, не произвольная ссылка участника. Пробник: `TestReviewMoveRejectsLoopback`.

### SEC-02 — P1 / высокая: чужой архив вызывает панику фонового импорта [тест]

Где: `internal/archive/full_read.go:63–75`, `internal/api/move_in.go:691–780`, рабочая горутина `runIncomingMove:432`.

Архив с допустимым manifest и таблицей blobs (`columns=[id,sha256,size_bytes]`, `rows=[[short]]`) проходит чтение таблиц и вызывает `index out of range [1] with length 1`. Проверка длины строки отсутствует перед `row[i]`. Пробник вызывает реальный `reviveMoveFile` на ZIP и ловит панику только в тесте. В рабочей горутине такой защиты нет: это выход за пределы recover HTTP-сервера и риск завершения всего процесса Wynd. Достаточно начать перенос со своего/скомпрометированного источника.

Похожие индексации есть в `reviveFromTables` для accounts/blobs. Там нужно отклонять также отсутствующие и повторяющиеся колонки, неверные типы, отрицательные размеры и несогласованные ссылки. Проверка должна предшествовать импорту файлов и изменениям БД. Защитный recover у фоновой задачи полезен, но не заменяет валидацию. Пробник: `TestReviewMoveRejectsShortBlobRow`.

### SEC-03 — P1 / высокая: входящий перенос не имеет общего бюджета ресурсов [код]

`handleStartIncomingMove` сравнивает с местом только `m.Bytes` из карточки источника. `pullMoveChunk:635–669` ограничивает один ответ 32 МиБ, но не общий заявленный Content-Range и накопленный временный файл; квота ImportBlob применяется позже. `FullReader.readJSON` разбирает распакованный JSON без лимита, а `Tables` держит все таблицы в памяти. Ограничение 256 МиБ в `/revive` к этому пути не применяется.

Намеренно неверная карточка/длинная последовательность диапазонов может занять диск до стадии импорта; сильно сжатая JSON-таблица — память при чтении ZIP. Исчерпание ресурсов на машине не запускалось: вывод основан на отсутствии проверки в прослеженном пути. Нельзя обозначать лимит чанка как лимит операции.

Доработка: общий резерв и предел временного файла с проверкой свободного места, разумный предел срока/числа активных операций, ограничения распакованного manifest/таблиц и количества записей, проверка арифметики размеров. Предпочтительно потоковое чтение крупных таблиц. Приёмка — малые искусственные лимиты и ограниченные тестовые данные, без настоящего заполнения диска.

### SEC-04 — P1: локальный toolchain содержит известные уязвимости [сканер]

Актуальный `govulncheck ./cmd/... ./internal/...` завершился кодом 3: **11 записей стандартной библиотеки с путями вызова**, ещё 1 в импортируемых пакетах и 3 в требуемых модулях без найденного вызова уязвимых функций. ## Хранение и исходящие действия

`servers.json` находится в пользовательском каталоге настроек ОС, `Wynd/workshop`. Профиль содержит имя, SSH-адрес, пользователя, способ входа, локальные галочки и короткий датированный результат последнего осмотра. В JSON нет паролей, ключей, сырых отчётов и журналов команд. Входной `last_check` не принимается от формы. Запись через временный файл и rename, чтение ограничено 4 МиБ. Проверена ошибка записи без изменения действующего снимка.

Пароли остаются в системной связке либо памяти операции. При входе без сохранения старый пароль удаляется, если им не пользуется другой профиль. Локальное отключение автоподключения не обращается к SSH или связке и не отменяет выполняющуюся работу. Изменение доступа и забывание занятого профиля отклоняются backend независимо от интерфейса.

Автоподключение выполняет только handshake и осмотр. Установка, обслуживание и доверие отпечатку требуют своего действия. Сохранённый результат помечен историческим; кнопки изменения сервера доступны после подключения и свежего осмотра. SSH-адреса и тексты сервера выводятся обычными текстовыми узлами Svelte. Новых HTTP-адресов загрузки, публичных API и путей отдачи файлов нет; используются прежние SSH, registry и GitHub self-update.

# Wynd Настольный: аудит оболочки — 17 ноября 2026

Повторный проход по [SECURITY](SECURITY.md) для окна для компьютера: прокси и мост браузера, локальный порт API, хранилище серверов, проверка адреса, самообновление и автозапуск. Отдельного аудита оболочки раньше не было — серверные выпуски, Мастерскую и отдельные исправления проверяли [другие отчёты](SECURITY.md#аудиты). Пункт плана — [58, раздел 3а](../plans/58-review-and-tail-checks.plan.md).

Срез: `cmd/wynd-desktop` и `internal/desktop` текущего дерева (окно 0.3.0, выпущено в `desktop-v0.3.0`); сервер и Мастерская в этот проход не входят.

## Модель доверия

Окно — тонкая оболочка вокруг выбранного сервера. Страница сервера живёт в `iframe` того же origin окна (`http://wails.localhost/`, `startURL` Wails 2.16) и получает мост `window.__wyndDesktop` с настоящим адресом сервера и `apiBase` локального порта. Значит, **выбранный сервер — доверенный код**: его страница может вызывать методы моста и обращаться к локальному порту. Это осознанно: человек сам добавил этот сервер. Остальные добавленные серверы доступны только как API и медиа через `/__srv/…`; мост в их ответы не вставляется, их страницы окно само не открывает.

Локальный порт API слушает `127.0.0.1` на случайном порту и проксирует выбранный сервер; адрес порта знает только страница окна. Вход — токен клиента в `Authorization`; паролей и токенов в файлах оболочки нет.

## Найдено и исправлено

| Граница | Находка | Исправление и доказательство |
|---|---|---|
| Локальный порт API, CORS | `corsHandler` подставлял в `Access-Control-Allow-Origin` любой origin запроса. Сайт в браузере, перебравший порты `127.0.0.1`, мог **прочитать** ответы прокси: страницу выбранного сервера, его публичный API и — при известном имени — добавленный сервер из локальной сети. Токен ему недоступен, поэтому закрытые данные не утекали, но читаемый обходной путь в локальную сеть был | Разрешены только origin'ы страницы окна: `wails.localhost`, `localhost`, `127.0.0.1`, `::1` (сборка Wails и `wails dev`). Чужой origin не получает `Access-Control-Allow-Origin`, и браузер отбрасывает ответ; preflight чужого сайта по-прежнему получает `204` без разрешения. Тест `TestCORSOnlyForWindowOrigins` |

Других находок о правах и данных в этом проходе нет; ниже — что проверено и признано безопасным, и принятые риски.

## Принятые риски

- **Выбранный сервер — доверенный код.** Его страница может вызвать методы моста: переключить источник, добавить адрес, включить автозапуск, запустить самообновление. Самообновление принимает только подписанный выпуск, автозапуск пишет только свой exe, поэтому установить чужое или выполнить произвольную команду через мост нельзя. Это та же модель, что у любого клиента сервера.
- **Локальные процессы того же пользователя.** Порт API и добавленные серверы доступны любому процессу на машине под этим пользователем; токена у него нет, поэтому он получает только то же, что мог бы запросить сам. Случайный порт и allowlist снижают поверхность, но не заменяют права ОС.
- **Общая банка cookies окна.** Проксированные серверы видят origin окна, поэтому cookie, поставленная одним добавленным сервером, ушла бы и другому. Сейчас это ни на что не влияет: Wynd не ставит cookies, вход — Bearer. Если в клиенте появится cookie-аутентификация, это надо пересмотреть (записано здесь, чтобы не забылось).
- **Один ключ подписи на все программы.** Компрометация закрытого ключа затронет Мастерскую и окно; ключ хранится у владельца, выпуски подписываются в «Подписи».
