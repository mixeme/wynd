## Находки

### R1 — высокая: гонка чанков разрушает загруженные данные

`internal/blob/upload.go:140-191`: два `WriteChunk` одной сессии с одним offset читают одинаковый `received_bytes` и пишут один `.part`. Первый успешно обновляет счётчик. Второй получает `RowsAffected()==0` и на строке 188 вызывает `f.Truncate(offset)`, откатывая файл первого.

Пробник детерминированно дал первому чанку завершиться, затем выпустил второй. Отклонение устаревшего чанка ожидаемо, но последующее завершение успешной сессии стало невозможным: `successful first chunk must remain completable after stale retry: blob: invalid`.

**Доработка:** сериализовать запись файла, обновление SQLite и rollback на уровне upload session. Простого удаления `Truncate` недостаточно: конкурирующая запись уже могла изменить содержимое.

### R2 — высокая: последний фрагмент считается скачиванием всего архива

`internal/api/fullarchive.go:558-565,851-887`: после ответа `206 Partial Content` `reachedEnd` проверяет только `end == size-1` и полную запись этого фрагмента. Получение предыдущих диапазонов не учитывается. Затем ссылка удаляется, а архив помечается скачанным и стирается.

Запрос `Range: bytes=<size-1>-` в пробнике получил один байт и удалил архив размером 11 804 байта. Это также несовместимо с параллельной или непоследовательной докачкой.

**Доработка:** безопасный минимум — удалять только после полного `200 OK`. Если завершение докачки должно удалять архив, хранить покрытие диапазонов для ссылки и ждать покрытия всего файла.

### R3 — высокая: параллельные запросы обходят квоту

`internal/api/journal.go:99-146,529-539` отдельно вызывает `CheckWriteQuota`, затем создаёт запись. `internal/blob/quota.go:256-289` читает использование и лимит без резервации. Между проверкой и записью другие запросы видят то же свободное место. Раздельные `CheckMediaQuota` и последующее использование blob имеют тот же структурный риск.

При квоте `before + TextCost("x")` 24 одновременных POST дали в пяти прогонах 24, 13, 12, 21 и 11 успешных созданий. Наибольший наблюденный результат: `used_before=873`, `used_after=26145`, `quota=1827`.

**Доработка:** атомарная резервация в SQLite до записи; подтверждение или освобождение резервации вместе с операцией. Проверка лимита и увеличение резерва должны быть одним сериализуемым действием.

### R4 — средняя: восстановление не включает текст в проверку места

`internal/api/revive.go:335-413`: `archiveBytes` суммирует только размеры blob; строка 369 сравнивает с лимитом именно её. `ReviveCircle` вставляет круг, после чего `res.TextBytes` добавляется к показываемому объёму.

Пробник восстановил круг с текстовыми записями при квоте 1 байт. Ответ — `201 Created`, фактическое использование — 2162 байта.

**Доработка:** до вставки вычислять файлы, записи, комментарии, реакции, события, имена и приветствие; проверять полный объём вместе с атомарной резервацией места.

### R5 — средняя: ссылка на архив сохраняет доступ после включения paywall

`internal/api/server.go:279,297` регистрирует `/full_archive/{token}` и `/full_archive_stream/{token}` без middleware платного участника. `validFullLink` в `internal/api/fullarchive.go:509-515` проверяет владельца и revision, но не текущее требование оплаты.

Это не анонимный доступ без секрета: нужна ранее выданная ссылка. Пробник создал ссылку, включил обязательную подписку и без входа скачал полный ZIP с ответом `200`. Динамически проверен обычный download route; stream route имеет ту же статическую проверку, но отдельно не воспроизводился.

**Доработка:** повторно проверять `PaymentRequired` для `link.accountID` при использовании ссылки, сохранив browser download без `Authorization`.

### R6 — средняя: предварительная оценка текста меньше фактического учёта

`internal/blob/quota.go:240-245` возвращает `550 + 400 + 4*len(text)`. Фактический учёт включает также имена автора и участника события; сравните `internal/chronicle/volume.go:54-91`. Поэтому проблема воспроизводится даже без гонки.

В одном прогоне R3 была создана только одна запись, но использование выросло с 873 до 1926 при квоте 1827.

**Доработка:** единая точная модель стоимости либо консервативная верхняя оценка, включающая имена и события. Нужны контрактные тесты Go-формул против SQL-триггеров, границы квоты, длинные и не-ASCII имена.

### R7 — низкая: тесты визуального сторожа устарели после приёмки C71

`docs/visual/workshop-baseline-guard.test.mjs:24-81` жёстко использует `c71-build` и ожидает состояние черновика. В `docs/visual/workshop-review-baselines.json` кадр уже принят и закреплён SHA. Тесты также ожидают ошибку `.tb differs`, хотя более ранняя проверка pinned SHA завершается раньше.

Результат `node --test docs/visual/workshop-baseline-guard.test.mjs`: 1 passed, 4 failed. Production `check:ui` и проверка реальных основ при этом проходят; это дефект тестового контура, а не свидетельство текущего визуального расхождения.

**Доработка:** изолированные синтетические frames/manifest для `draft`, `rejected`, `approved`; отдельно проверять pinned hash, chrome, evidence и body changes. Не ослаблять действующие проверки основ.

## Оптимизация

Широкая оптимизация без измерений не рекомендуется. Go-бенчмарков в проекте не обнаружено; production build и тесты не доказывают производительность.

### Главный кандидат — холостая сборка архива

`internal/archive/archive.go:52-56,112-128,734-749` и `internal/archive/full.go:109-118`: перед реальной отдачей `Size`/`FullSize` выполняют холостую сборку. Медиа не читаются, но через ZIP-писатель копируются нули объёмом всех файлов; HTML и JSON формируются повторно. Это потенциальный расход CPU и памяти по пропускной способности на больших архивах, не двойное чтение исходников.

Сначала benchmark на репрезентативных данных. Затем сравнить арифметический расчёт ZIP-размера, однопроходную сборку во временный файл и поток без заранее известного `Content-Length` с учётом требований продукта.

### База данных

Проверка квоты выполняет несколько агрегатных запросов. Объединять их следует после исправления атомарности и по результатам `EXPLAIN QUERY PLAN`/замеров. Кэширование `usedBytes` без модели инвалидации добавит риски.

Лента уже имеет курсорные порции (`internal/chronicle/snapshot_page.go`), поиск использует FTS5 (`internal/search/search.go`), у `posts` есть индексы по кругу и датам. Новая подсистема кэширования или замена загрузки ленты сейчас не обоснованы.

### Что уже разумно

- Архивы пишутся потоком, а не собираются целиком в память.
- JPEG/WebP/MP4 не сжимаются повторно через Deflate.
- Журнал SSH ограничен хвостом и обновлениями не чаще 400 мс.
- Desktop production bundle: JS 172,71 КБ, CSS 64,62 КБ до gzip.
- Штатные автоматические проверки поведения обширны.
